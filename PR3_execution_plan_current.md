## 0. Цель, границы и уже согласованные решения

**Тема ПР3:** «Сравнительный анализ моделей конкурентности для REST-сервиса: нативные Java-потоки, виртуальные Java-потоки, Kotlin coroutines, goroutines».

**Цель текущей ПР3:** на основе научных публикаций обосновать методику и спроектировать воспроизводимый экспериментальный стенд, а не проводить полный эксперимент ВКР или реализовывать промышленную систему.

**Четыре сравниваемые реализации:**
1. Java platform threads (платформенные/«нативные» потоки) — REST-сервис Java/Spring.
2. Java virtual threads — REST-сервис Java/Spring.
3. Kotlin coroutines — REST-сервис Kotlin/Spring, с реальной приостановкой на I/O (не блокировать диспетчер некорректно).
4. Go goroutines — REST-сервис Go, за пределами JVM.

**Зафиксированные сценарии:**
- **I/O-bound:** k6 вызывает `GET /io`; SUT выполняет HTTP-вызов к **отдельному контролируемому сервису-эмулятору**, который отвечает через фиксированную задержку (стартовая гипотеза для настройки — 100 мс) без CPU busy-wait; SUT возвращает результат. **База данных в базовом плане не используется.** Нельзя допускать, чтобы эмулятор или его сеть становились узким местом.
- **CPU-bound:** k6 вызывает `GET /cpu`; SUT многократно вычисляет SHA-256 над фиксированными входными данными и возвращает проверяемый итог. Число итераций калибруется перед основными тестами (ориентир 50–100 мс вычислений на запрос в контрольных условиях; не окончательная цифра). Проверить семантическую эквивалентность и не допустить исключения вычислений оптимизатором. Отличия библиотек хеширования учитывать как угрозу валидности.
- **Внешняя нагрузка:** k6 генерирует HTTP-запросы для всех реализаций; варианты SUT тестируются **по очереди**, а не конкурируют друг с другом за одни и те же ресурсы.

**Методологическое ограничение:** три реализации работают на JVM, Go — на другой среде выполнения. Выводы о различиях всего REST-стека нельзя автоматически приписывать исключительно моделям конкурентности. Разделить интерпретацию на сравнение внутри JVM и межплатформенное сравнение.

**Не входит в обязательный результат ПР3:** реализация всех четырёх SUT, проведение 240 основных измерений и публикация реальных benchmark-результатов. Если для убедительного проектирования будет нужен небольшой технический прототип, согласовать это отдельно.

## 1. Общие правила выполнения

- Идём **строго последовательно по этапам 1–7**; по завершении этапа **сохраняем результаты в самостоятельные файлы**, показываем ссылки на них, коротко сверяем критерии готовности и отмечаем статус.
- **Не выдавать планы/ожидания за измеренные результаты.** Для параметров, ещё не подкреплённых статьями или калибровкой, явно писать «предварительно» и описывать способ окончательного выбора.
- Не придумывать научные публикации, содержание методики, DOI, наличие кодовых артефактов, версии инструментов или результаты тестов. Все библиографические и технические сведения проверять по первоисточникам.
- Использовать результаты предыдущих НИР как контекст и кандидатов на литературу, но не заменять ими проверку оригинальных научных статей.
- Любые существенные изменения согласованных решений (набор моделей, сценарии, SUT/фреймворки, основные метрики, первичная гипотеза, состав эксперимента) **сначала показать на согласование**. Незначительные уточнения (формулировка, структура, исправление ошибки) фиксировать в журнале и сообщать пользователю.
- Вести **версию, чеклист статусов, журнал изменений и решений** в этом документе. При обсуждении опираться на номер этапа, сохранённые файлы и критерий готовности.

## 1.1. Обязательное сохранение результатов каждого этапа

**Правило:** каждый этап из раздела «Последовательность этапов» (1–7) завершается **не только текстом в переписке, но и созданием одного или нескольких отдельных файлов**. Эти файлы — исходные материалы будущего итогового отчёта. Нельзя считать этап завершённым, если его результаты существуют только в сообщениях чата.

**Единая структура хранения:** корень `PR3_artifacts/`; результаты каждого этапа лежат в отдельном каталоге `stage_01/` ... `stage_07/`. Имя файла должно отражать содержание, формат должен быть удобен для повторного использования (Markdown для текста; CSV/XLSX для таблиц при необходимости; `.mmd` для Mermaid; JSON/YAML для структурированных конфигураций). При необходимости можно одновременно сохранять человекочитаемый и машинно-обрабатываемый варианты.

**Регламент работы с файлами:**
1. После завершения этапа создать и проверить существование всех его обязательных файлов. Материалы должны быть **полными для данного этапа**, а не пустыми шаблонами.
2. В сообщении на ревью дать ссылки на файлы, кратко описать результат и подтвердить критерии готовности этапа.
3. При замечаниях обновить соответствующие файлы до принятия этапа; при существенных правках уже принятого этапа зафиксировать причину, новую версию и влияние на последующие этапы. **Не перезаписывать незаметно утверждённый результат.**
4. Сразу обновить в текущем плане таблицу статусов и список файлов; **этап считается принятым после ревью пользователем**.
5. При сборке итогового отчёта использовать именно сохранённые и принятые файлы, сверять согласованность терминов, ссылок, гипотез, спецификаций и расчётов. Не подменять содержимое файлов воспоминаниями из переписки.
6. Для продолжения в новой беседе использовать актуальную версию плана и каталоги результатов: долговременная память в проекте отключена, поэтому **файлы — источник сохранённого состояния**.

## 1.2. Публикация утверждённых артефактов в Project Sources

**Цель:** сохранять актуальный план и принятые результаты этапов в общих источниках проекта «Уник», чтобы ими можно было пользоваться из других чатов проекта без опоры на долговременную память или на историю конкретного чата.

**Регламент:**
1. **Текущий план:** хранить в Project Sources актуальную утверждённую версию `PR3_execution_plan_current.md`. После изменения плана предоставлять новую версию для обновления источника.
2. **Каждый этап:** сначала создать самостоятельные файлы в `PR3_artifacts/stage_XX/`, передать пользователю на ревью, внести замечания. **Только после явного апрува пользователя** представить окончательные файлы для добавления в Project Sources; непроверенные черновики туда не публиковать.
3. **Техническая граница:** текущий инструментарий ассистента не поддерживает прямую загрузку файлов в интерфейс Project Sources. Пользователь выполняет действие в проекте: **Sources / Источники → Add sources / Добавить источники → загрузить файл**. Ассистент предоставляет готовые файлы и напоминает об этом шаге после апрува. Дополнительно отдельный полезный ответ можно сохранить через меню сообщения **Add to project sources**.
4. **Обновления:** при новой утверждённой версии заменять или явно архивировать устаревшую версию в Project Sources, чтобы не возникало конфликта источников. Указывать номер версии и дату в документе.
5. **Новая беседа:** начинать с чтения `PR3_execution_plan_current.md` и принятых файлов `stage_XX` из Project Sources; ориентироваться на их статус и журнал изменений. Не считать обсуждение в другом чате достаточной заменой файлов.
6. **Если в будущем появится доступный инструмент прямого добавления в Project Sources**, можно автоматизировать загрузку, но до подтверждения успешного добавления не утверждать, что файл уже находится в источниках проекта.

**Важно:** наличие файла в каталоге `/mnt/data` или ссылки `sandbox:/...` само по себе **не означает**, что этот файл добавлен в Project Sources.

## 2. Последовательность этапов и критерии готовности

### Этап 1. Подбор научных публикаций
**Действия:** просмотреть списки источников НИР1/НИР2, проверить оригиналы и дополнить исследованиями goroutines/Go и сопоставимыми benchmark-работами. Составить основную подборку минимум 6 публикаций и при необходимости резерв.

**Обязательные ограничения подборки:** ≥6 статей; ≥4 с реальными экспериментами; ≥3 за последние 5 лет относительно даты подготовки отчёта; ≥2 из рецензируемых изданий (ACM/IEEE/Springer/Elsevier или соответствующие научные издания); желательно ≥1 с доступным кодом/датасетом/образом.

**Выход:** библиографический список с DOI/URL, годом, типом издания, кратким описанием релевантности, подтверждением экспериментальности и информации об артефактах.

**Критерий готовности:** для каждой статьи есть проверяемый первоисточник; квоты соблюдены; распределение по JVM, Kotlin и Go обеспечивает релевантность теме; отсутствие артефактов не скрыто.

### Этап 2. Методологический анализ статей и синтез
**Действия:** для каждой выбранной статьи заполнить отдельную строку сводной таблицы по **12 полям**: (1) библиография; (2) RQ/гипотеза; (3) объект; (4) независимые факторы и уровни; (5) метрики и единицы; (6) контролируемые условия; (7) стенд и инструменты; (8) методика (повторения, прогрев, длительность, порядок); (9) статистика; (10) угрозы валидности; (11) артефакты и ссылки; (12) оценка воспроизводимости 0–3 с объяснением.

**Шкала воспроизводимости:** 0 — недостаточно деталей; 1 — есть методика, нет артефактов; 2 — артефакт есть, но окружение не зафиксировано; 3 — артефакт и зафиксированное окружение / скрипты запуска. Неуказанное в статье отмечать **«не указано»**, а не домысливать.

**Синтез (1–2 страницы):** распространённые метрики и методики, типовые ошибки, сравнение качества экспериментов, выводы для нашего стенда со ссылками на соответствующие статьи.

**Выход:** сравнительная таблица и синтез.

**Критерий готовности:** это анализ экспериментальных дизайнов, а не пересказ содержания статей; указаны сильные и слабые стороны, подтверждённые публикациями.

### Этап 3. Научная постановка и критерии научности
**Действия:** уточнить один основной RQ и, при необходимости, уточняющие RQ для JVM и Go; сформулировать H₀ и направленную H₁; заранее определить, что их опровергает; выбрать основной сравнительный показатель и вторичные метрики.

**Независимые факторы:** модель конкурентности (4 уровня), тип нагрузки (2 уровня), уровень входящей нагрузки (предварительно 3 уровня; точные RPS — после калибровки/литературы).

**Зависимые метрики:** успешный RPS (запросов/с), задержка p50/p95/p99 (мс), доля ошибок и тайм-аутов (%), CPU (в согласованных единицах), RSS/peak memory (MiB); JVM/Go heap и GC — отдельно интерпретируемые диагностические метрики; показатели нитей/горутин/переключений — диагностические.

**Контроль:** одинаковая бизнес-логика и ответы, payload, входной профиль, тайм-ауты, CPU/RAM, базовые настройки сети, длительность, прогрев, метод сбора данных, контролируемый внешний API и количество соединений. Для JVM — одинаковые JDK/JVM/GC-параметры по возможности; особенности Go явно фиксировать.

**Критерии научности:** объект и метрики определены операционально; контроль переменных; repeatability, reproducibility и replicability с различающимися сценариями; внутренняя, внешняя, конструктная и статистическая валидность; фальсифицируемость.

**Практически значимый эффект:** установить порог (например, требуемый выигрыш в устойчивой пропускной способности при ограничениях на p95 и ошибки) **после изучения статей**; не выдавать произвольное число за научно подтверждённое.

**Выход:** RQ, H₀/H₁, таблица переменных, метрики/единицы/источники, критерий успеха и критерии научности.

**Критерий готовности:** гипотезы допускают опровержение, не предполагают универсального превосходства Go или виртуальных потоков, а каждое утверждение измеримо.

### Этап 4. Проверяемость и воспроизведение другими разработчиками
**Действия:** описать фиксацию версии кода (Git tag), зависимостей (Gradle lockfiles / Go modules+go.sum), контейнерных образов (версии/digests), тестовых входов (SHA-256), параметров нагрузки (конфиги), случайных сидов (для перемешивания порядка, если применимо), средств запуска (`make`/`just`), метаданных прогонов (JSON-манифест), независимой проверки (CI).

**Выход:** таблица по всем уровням проверяемости и **исполняемый сценарий** для проверяющего: подготовка → старт окружения → проверка корректности эндпоинтов → прогрев → запуск серии → сбор CSV/JSON и метрик → анализ → проверка допусков. Указать, что именно обязано совпадать точно (семантика/ответ), а что — в пределах заданного допуска (измеренные показатели) и как определяется этот допуск.

**Критерий готовности:** проверяющий понимает перечень команд, входных файлов, ожидаемых результатов и ограничений сравнимости на другом железе; CI может проводить сокращённую техническую проверку без подмены полноценного benchmark.

### Этап 5. Проект экспериментального стенда
**Действия:** создать диаграмму Mermaid как код; описать 5 частей стенда: SUT (4 варианта), источник нагрузки k6, сбор измерений, хранилище сырых данных + метаданных, аналитические скрипты. Вынести контролируемый HTTP-эмулятор как отдельный компонент I/O-сценария.

**Предварительные технологии:** Java/Spring Boot для platform и virtual threads; Kotlin/Spring для suspend-обработки; Go/net/http; k6; JVM Actuator/Micrometer + Prometheus; Go runtime exporter / Prometheus; системные метрики контейнеров; JFR и pprof только в отдельных диагностических сериях; Python для статистики; Docker Compose для оркестрации.

**Спецификации:** таблица «компонент → роль → технология и точная версия → образ/digest → обоснование со ссылкой на статьи», описание железа и ОС, ресурсов контейнеров (`cpus`, `mem_limit`), JVM/Go-настроек, сетевых условий и изоляции k6/эмулятора. Подготовить дерево каталогов с назначениями (`services/`, `load/`, `monitoring/`, `configs/`, `analysis/`, `results/`, `docs/`, `scripts/`, `ci/`).

**Критерий готовности:** есть диаграмма с потоками запросов и метрик, конкретные роли компонентов, спецификация окружения и репозитория; исключено узкое место в эмуляторе/генераторе; решения обоснованы литературой.

### Этап 6. Факторный план, статистика, проверка стенда, угрозы
**Предварительный полный план:** 4 модели × 2 сценария × 3 уровня нагрузки = **24 конфигурации**. Минимум **5 повторений на конфигурацию** по заданию, предпочтительно **10** (тогда **240 измерительных прогонов**). Окончательные уровни нагрузки и количество повторов обосновать статьями, ожидаемым разбросом и возможностями стенда.

**Методика:** фиксированный прогрев JVM/Go и эмулятора до измерений, единая длительность окна измерения, сброс состояния между конфигурациями, рандомизация/блокирование порядка, независимые прогоны. Заранее определить параметры open-model k6 и способ контроля фактически достигнутой интенсивности.

**Единица анализа:** один **прогон** (например, p95 за прогон), а не отдельный HTTP-запрос. Для каждой конфигурации — медиана/среднее, разброс, доверительные интервалы; статистические сравнения/множественные проверки выбрать исходя из данных и дизайна; отчёт об эффекте и интервалах важнее одного p-value.

**Проверка стенда:** A/A для одной конфигурации (не только отсутствие «значимости», но и проверка практически допустимого разброса); CPU/сеть/ошибки k6; достаточная ёмкость эмулятора; проверка эквивалентности ответов и известного SHA-256; синхронизация временных меток; влияние мониторинга.

**Таблица угроз:** платформа/фреймворки, компиляторы и криптобиблиотеки, JIT/GC/Go runtime, connection pool, ограничение источника нагрузки, насыщение HTTP-эмулятора, фоновые процессы, порядок прогонов, сетевые флуктуации, разница в измерителях, перенос на другое железо. Напротив каждой — конкретная мера.

**Критерий готовности:** есть исчислимый полный/дробный план, число прогонов, прогрев и рандомизация, заранее описанная статистика, A/A и таблица «угроза → мера».
