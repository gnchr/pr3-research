## 1. Объект, предмет и границы исследования

**Объект исследования** — функционально эквивалентные REST-сервисы, обрабатывающие конкурентные HTTP-запросы с разным характером прикладной работы.  
**Предмет исследования** — связь выбора модели конкурентного выполнения и реализации серверного стека с измеримыми показателями: задержкой, пропускной способностью, масштабируемостью, потреблением CPU/RAM, работой GC, накладными расходами конкурентности и устойчивостью к перегрузке.

**Цель** — предложить проверяемую методику для определения, в каких нагрузочных условиях исследуемые реализации обладают практически значимыми различиями в производительности REST-обработки, и какому расходу ресурсов соответствуют эти различия.

| Код | Вариант SUT | Что можно интерпретировать |
|---|---|---|
| **J-PT** | Java 21, Spring MVC, платформенные потоки | Базовая JVM-конфигурация и точка сравнения |
| **J-VT** | **Тот же Java-артефакт**, Spring MVC, виртуальные потоки | Наиболее контролируемый эффект типа потока/соответствующей серверной конфигурации относительно J-PT |
| **K-CO** | Kotlin, Spring MVC, `suspend` и действительная приостановка HTTP-клиента (`awaitBody`/`awaitSingle`) | Эффект Kotlin coroutine-based REST-реализации, в том числе различий диспетчеризации и асинхронного пути запроса |
| **G-GO** | Go, `net/http`, goroutines | Межплатформенная эффективность Go REST-реализации **в целом**; не изолированный эффект только goroutines |

По утверждённому проекту стенда J-PT/J-VT запускаются из **одной сборки**, а для Kotlin используется сопоставимый Spring MVC/Tomcat и тот же JVM HTTP-клиент (различается способ ожидания). Для Go смена языка, runtime, серверных и клиентских библиотек неизбежна. Это прямо ограничивает причинные выводы [A1, A2, A5, A6].

**Два фиксированных вида работы:**

- **I/O-bound, `GET /io`:** один запрос к отдельному контролируемому HTTP-эмулятору `GET /delay`, номинальная задержка эмулятора **100 мс** (проектный ориентир), проверка маркера `OK`, возврат одинакового JSON-результата; PostgreSQL и искусственный `Thread.sleep` внутри SUT **не используются**. Эмулятор ждёт по таймеру без busy-wait.
- **CPU-bound, `GET /cpu`:** последовательная цепочка `state = SHA-256(state)` с **ровно 32 нулевыми байтами** на входе и фиксированным для всех четырёх SUT числом итераций `N`, канонический проверяемый digest в ответе. `N` выбирается один раз в пилоте на **общем контрольном варианте**, ориентировочно для длительности 50–100 мс, затем неизменен для других реализаций. Подбор отдельного `N` для каждого языка ради одинакового времени **запрещён**: это сделало бы объём вычислений разным.

Источник воздействия — один и тот же k6 с открытой моделью поступления HTTP-запросов (`constant-arrival-rate`; одна итерация = один запрос к выбранному SUT). Все реализации тестируются **последовательно**, каждая в одинаковой квоте CPU/RAM. k6 и эмулятор используют отдельные, контролируемые ресурсы. Это проект, а не реализованный стенд.

## 2. Исследовательские вопросы (RQ)

**Основной RQ.** *Как различается максимальная подтверждённая устойчивая успешная пропускная способность между Java virtual threads и Java platform threads в I/O-bound REST-сценарии при одинаковых ограничениях по p95 и ошибкам, а также как четыре реализации ведут себя на одинаковых фиксированных уровнях нагрузки в I/O- и CPU-bound сценариях с учётом CPU/RAM?*

**RQ1 (основной подтверждающий, внутри JVM).** *Обеспечивает ли использование Java virtual threads в том же Spring REST-сервисе более высокую максимальную устойчивую пропускную способность, чем platform threads, при I/O-bound нагрузке и одинаковых требованиях к качеству обслуживания?*

**RQ2 (внутри JVM, фиксированная нагрузка).** *Как Kotlin coroutines, Java virtual threads и Java platform threads различаются по успешному RPS, p95, ошибкам и расходу CPU/RAM на общих уровнях `L1–L3` для `/io` и `/cpu`?*

**RQ3 (межплатформенное сравнение, фиксированная нагрузка).** *Каковы успешный RPS, p95, ошибки и ресурсная эффективность Go/net/http относительно JVM-реализаций на общих `L1–L3`, учитывая, что нельзя выделить эффект goroutines отдельно от всего стека Go?*

**RQ4 (характер нагрузки).** *Как меняются сравнительные показатели четырёх реализаций (успешный RPS, p95, ошибки, CPU/RAM) между I/O-bound и CPU-bound сценариями на фиксированных нагрузках `L1–L3`?*

**Граница охвата (согласовано 16.11.2026):** только для `J-PT/io` и `J-VT/io` дополнительно исследуется граница устойчивости и оценивается `C`. Для `K-CO`, `G-GO` и любого `/cpu` **не ищем максимальную ёмкость**, а сравниваем успешный RPS и качество обслуживания только на общих `L1–L3`. Это сознательное ограничение эксперимента, а не свидетельство равенства/отсутствия преимуществ. RQ1 — **единственная главная подтверждающая гипотеза**, RQ2–RQ4 — вторичные исследовательские вопросы, проверяемые только в указанном ограниченном объёме.

## 3. Гипотезы и фальсифицируемость

### 3.1. Основная направленная гипотеза: J-VT против J-PT на I/O

**Основная метрика — максимальная устойчивая успешная пропускная способность** `C` (корректных HTTP-ответов/с), измеренная на I/O-bound сценарии при *одних и тех же* требованиях качества обслуживания. `p95` из k6 и доля неуспешных запросов служат **условиями допустимости** пропускной способности, а не самостоятельной первичной метрикой.

Для каждого варианта SUT исследуем устойчивые режимы заданной входной интенсивности `λ` (запросов/с). Режим признаётся допустимым только если **в заранее согласованной доле независимых прогонов** одновременно:

- `p95_success(λ) ≤ T_p95` — end-to-end p95 корректно завершённых запросов не хуже допустимого предела `T_p95` (мс);
- `errors(λ) ≤ E_max` — доля ошибок/тайм-аутов среди действительно начатых запросов не больше `E_max` (%), при проверке правильности payload;
- генератор k6 фактически обеспечивает заданную интенсивность с допуском `Q_arrival`, не исчерпывает собственные ресурсы; `dropped_iterations` и инциденты эмулятора учитываются отдельно; условия выдерживаются на стационарном измерительном окне после прогрева.

**`T_p95 = 200 мс`, `E_max = 1%` и `δ_min = 15%` приняты пользователем как **предварительные ориентиры**. Окончательные значения до основной серии, а также `Q_arrival` и необходимая доля успешных независимых прогонов, пока не зафиксированы.**

**Уточнение от заказчика учебного проекта (15.11.2026):** реальных эксплуатационных SLO/SLA у REST-сервиса **нет**. Поэтому значения `T_p95`, `E_max` и `δ_min` в этой работе должны выступать **исследовательскими критериями приемлемого качества**, а не требованиями внешнего клиента или якобы нормативами из литературы. Предлагаемый порядок: (1) проверить отдельной технической калибровкой фактическую задержку эмулятора и низконагруженного HTTP-тракта; (2) до основных сравнительных серий согласовать и публично зафиксировать единый для всех SUT бюджет p95, предел ошибок и минимальный интересующий эффект по устойчивому RPS; (3) не менять пороги после получения сравнительных результатов. `T_p95 = 200 мс` при номинальных 100 мс внешнего ожидания — **принятый предварительный бюджет** (100 мс ожидание + условный резерв на обработку, сеть и очереди), а не измеренное значение или вывод из статей. `E_max = 1%` и `δ_min = 15%` — **принятые предварительные инженерные ориентиры**: их применимость и точность оценивания подлежат проверке до основного теста; окончательные значения должны быть отдельно зафиксированы после пилота. Для `δ_min` нужна достаточная разрешающая способность сетки RPS, которую уточняет этап 6.
 Сначала предпочтительны реальные требования сервиса (SLO/SLA); если их нет, можно выбрать проверяемые инженерные бюджеты на основе независимой калибровки эталонного низконагруженного тракта, задержки эмулятора и качества измерений. Выбор и его источник публикуются **до подтверждающих измерений**, а не после просмотра того, кто выиграл. Согласованные предварительные ориентиры p95 ≤ 200 мс при проектном эмуляторе 100 мс и ошибки ≤ 1% не являются нормативами из A1–A7 и требуют проверки на реальном стенде до окончательной фиксации.

`C_PT` и `C_VT` — оценки **наибольшего устойчиво достигаемого успешного RPS** при выполнении этих условий для J-PT и J-VT соответственно. Оценка требует заранее определённой процедуры поиска/проверки нагрузочной границы и независимых повторов. При дискретной сетке нагрузок она является **максимальным подтверждённым уровнем из исследованных**, а не точным физическим максимумом. При обнаружении первой недопустимой ступени можно указать интервал между последней допустимой и первой недопустимой, но нельзя интерполировать недоказанную точную ёмкость.

Обозначим `ρ = C_VT / C_PT` при `C_PT > 0` и `δ_min > 0` — заранее выбранную минимально существенную относительную прибавку устойчивой пропускной способности.

- **H₀:** `ρ ≤ 1 + δ_min` — практически значимое преимущество J-VT по устойчивому RPS не установлено.
- **H₁ (направленная):** `ρ > 1 + δ_min` — J-VT обеспечивает более высокую устойчивую пропускную способность на величину, превышающую порог практической значимости, при одинаковых пределах p95 и ошибок.

**Правило подтверждения H₁:** доверительный интервал для `ρ`, полученный на уровне **независимых прогонов/блоков**, должен с заранее выбранной доверительной вероятностью исключать `1 + δ_min` в сторону большего значения (проектно — нижняя граница одностороннего 95%-го интервала строго больше порога). Одновременно должны быть выполнены критерии p95, ошибок, корректности ответов и технической пригодности генератора/эмулятора. Конкретный метод оценивания ёмкости, границ интервала и мощности теста относится к этапу 6 и утверждается до запуска; отдельные запросы не превращаются в независимые наблюдения.

**Опровержимость и неопределённость:** если J-VT выдерживает не больше нагрузки, чем J-PT, выигрыш не достигает `δ_min`, либо доверительный интервал допускает отсутствие существенного эффекта, **H₁ не получает подтверждения**. Это не доказывает H₀. Если измерены только режимы, где J-PT и J-VT проходят критерии на всех испытанных ступенях, верхний предел их ёмкости не установлен и объявлять победителя по «максимуму» нельзя — требуется дополнительная проверка границы либо честный ограниченный вывод.

**Почему выбран вариант Б:** виртуальные потоки не сокращают внешние 100 мс ожидания эмулятора как таковые; исследовательская ценность — сколько ожиданий и запросов сервис способен обслужить одновременно **без неприемлемых очередей и отказов**. Статьи [A1, A3] обосновывают зависимость эффекта от типа/интенсивности нагрузки, [A5, A6] — контроль независимых факторов и статистический анализ. Ни одна из A1–A7 не задаёт универсальных численных `δ_min`, `T_p95`, `E_max` для нашего сервиса.

### 3.2. Вторичные, заранее перечисленные сравнения

| Сравнение | Ожидаемое направление / исследовательская позиция | Роль |
|---|---|---|
| K-CO против J-PT на `io/L1–L3` | Возможное улучшение успешного RPS и p95 благодаря неблокирующему ожиданию; **не постулируем обязательное превосходство** | Вторичное JVM-сравнение на общих фиксированных нагрузках |
| K-CO против J-VT на `io/L1–L3` | Направление заранее неизвестно; успешный RPS, p95, ошибки и ресурсы без оценки `C` для Kotlin | Исследовательское, без утверждений о максимальной ёмкости Kotlin |
| G-GO против J-PT/J-VT/K-CO на `io/L1–L3` | Направление заранее неизвестно; оценивается **эффективность всего Go-стека** на одинаковых нагрузках | Межплатформенное сравнение, без поиска максимального `C` Go |
| Все четыре модели на `/cpu` | Не ожидается универсального выигрыша облегчённых единиц выполнения: ограничение создаёт CPU; сравниваем возможные дополнительные расходы | Контроль типа нагрузки; не выдаём отсутствие значимости за доказательство эквивалентности |
| Высокая нагрузка / приближение к насыщению | Ожидается рост p95 и, возможно, доли ошибок у некоторых реализаций; границы допустимой нагрузки могут отличаться | Анализ масштабируемости и устойчивости |

Для вторичных пар приводятся отношения **успешного RPS при одинаковой заданной входной интенсивности**, оценки p95 и ошибок, 95%-е интервалы (если методически обеспечены), эффекты и явная пометка об исследовательском характере. Если будут формальные вторичные тесты гипотез, их семейства и коррекция множественных сравнений задаются **до измерений** на этапе 6. Это **не независимые подтверждения H₁**.

### 3.3. Ограничения причинных утверждений

Наиболее контролируемый контраст — **J-PT vs J-VT** при одном Java-артефакте и общих настройках, хотя смена механизма обработки запросов может влечь отличия исполнительного пути и служебных потоков: это тоже следует проверять. Контраст с **K-CO** включает код контроллера, неблокирующий путь клиента и coroutine runtime; с **G-GO** — дополнительно язык, GC, HTTP-сервер и сетевые библиотеки. В выводах не допускается формулировка «goroutines на X% быстрее virtual threads» без уточнения, что измерен **комплекс конкретных REST-реализаций** [A2, A5, A6].

## 4. Независимые переменные и план уровней

| Фактор | Уровни | Как задаётся и что важно |
|---|---|---|
| **F1. Реализация/модель конкурентности** | `J-PT`, `J-VT`, `K-CO`, `G-GO` (**4**) | Один активный SUT на прогон; код/конфигурация зафиксированы в манифесте |
| **F2. Тип работы** | `io`, `cpu` (**2**) | `/io` → реальный внешний HTTP-эмулятор; `/cpu` → фиксированная цепочка SHA-256 |
| **F3. Интенсивность входящей нагрузки** | `L1` — низкая, `L2` — средняя, `L3` — высокая (**3**) | Открытая модель k6; задаётся **целевой RPS**, а не только числом VU; точные значения определяются отдельным пилотом и фиксируются перед основной серией |

**Предварительный полный факторный план:** `4 × 2 × 3 = 24` конфигурации. Рекомендуемые `10` независимых измерительных прогонов на конфигурацию: `240` прогонов, не включая прогрев и калибровку. Минимум из задания — **5** на конфигурацию. Этот расчёт согласован с этапом 5 и не означает, что тесты уже проведены. Подробное распределение повторов/блоков, порядок испытаний и длительности относятся к этапу 6.

**Формирование `L1/L2/L3`:** калибруются генератор, эмулятор и контрольный J-PT (отдельно по `/io` и `/cpu`); проектное правило из этапа 6 — 20%, 60%, 100% от контрольной устойчивой нагрузки сценария, одинаковые уровни для всех четырёх SUT в этом сценарии. Точные RPS фиксируются только после независимого пилота до подтверждающего сравнения. Три фиксированных уровня дают срез характеристики, а не физический максимум. **Согласованный этап 6 дополняет матрицу `4×2×3` = 24 конфигурации (240 основных прогонов) поиском границы только для `J-PT/io` и `J-VT/io`**: проектно 4–8 дополнительных ступеней на каждую модель × 10 повторов, всего ориентировочно 320–400 прогонов без пилота/A/A. Для Kotlin, Go и CPU **максимум C не оценивается**. Шаг у границы проектно ≤5%; фактические ступени и техническая пригодность подлежат независимому пилоту и фиксации до основной серии. Статьи [A1, A3, A5, A6] мотивируют различать входящий поток и число пользователей, но не задают эти числа.

**Не являются самостоятельными факторами основного плана:** версия JDK, объём памяти, число CPU, алгоритм GC, длительность задержки эмулятора, `N` для SHA-256, HTTP-тайм-аут и лимит соединений. Все они должны быть заранее зафиксированы (см. §6), иначе факторный план перестанет отвечать RQ. CPU и GC метрики измеряются, но **GC-алгоритм не варьируется** в базовом эксперименте, в отличие от [A4].

## 5. Зависимые переменные: операциональные определения

**Общий принцип:** измерение проводится за одно одинаково определённое **измерительное окно** после прогрева. Единица анализа — **независимый прогон**, а не отдельный HTTP-запрос. Для каждого прогона сохраняются сырые данные и итоговая запись с `run_id`, факторами, параметрами и флагом пригодности. Конкретное правило включения запросов на границе окна и завершения запросов после окончания подачи уточняется до эксперимента в этапе 6 и одинаково для всех SUT.

| Критерий (из НИР 2) | Показатель и единица | Как именно измеряется / интерпретируется |
|---|---|---|
| **1. Пропускная способность (первичная)** | **Максимальная устойчивая успешная пропускная способность `C`**, корректных запросов/с | Из повторных прогонов на разных заранее выбранных уровнях интенсивности: наибольший подтверждённый успешный RPS, при котором одновременно выдержаны p95 ≤ `T_p95`, ошибки ≤ `E_max` и технические критерии. Для каждого прогона исходная метрика `N_success / T_measurement`; отдельно целевой/фактический входящий RPS и `dropped_iterations`. Одна точка RPS не определяет максимум |
| **2. Задержка** | **p50, p95, p99**, мс | k6 измеряет end-to-end время HTTP-запроса; перцентили считаются для успешно завершённых корректных ответов в рамках **одного прогона**; неуспешные запросы, тайм-ауты и их длительности сохраняются отдельно, чтобы p95 нельзя было улучшить отбрасыванием работы |
| **3. Масштабируемость** | Зависимость успешного RPS, p95, ошибок от интенсивности; интервал возможной границы устойчивости | По ступеням фиксируем последнюю допустимую/первую недопустимую интенсивность; **3 уровня не дают точный максимум**. Процедура уточнения границы — на отдельное согласование в этапе 6 |
| **4. CPU** | Средняя нагрузка, **CPU-секунды/с** (= эквивалент задействованных ядер); CPU-с/успешный запрос | cAdvisor/cgroup: прирост накопленного CPU-времени контейнера SUT за окно / длительность окна; также процент относительно одинаковой CPU-квоты. CPU k6 и эмулятора — отдельно |
| **5. Память** | **RSS и пиковая RSS**, MiB; JVM heap/Go heap — отдельно | Контейнерная память через один cgroup/cAdvisor-контракт для сравнения всех SUT; peak в окне, также working set как дополнительная метрика; сравнение JVM heap и Go heap напрямую не заменяет сравнение RSS |
| **6. Влияние GC** | Число сборок; паузы GC, мс; суммарное время GC; при наличии аллокации Б/с | Для JVM — Micrometer/JVM/JFR/GC logs; для Go — `runtime/metrics`/pprof. Обе среды имеют разные GC: метрики приводятся **с определением каждого runtime**, а не сводятся к одному некорректному числу |
| **7. Накладные расходы конкурентности** | Число платформенных потоков, виртуальных потоков, корутин/горутин; переключения контекста/с | JVM JFR/системные средства, Go runtime/pprof и cgroup/ОС. Количество потоков/корутин/горутин — **объясняющие, не полностью взаимозаменяемые показатели**; расширенное профилирование вынесено в отдельные серии |
| **8. Устойчивость** | Неуспешные запросы, %, тайм-ауты/отказы, восстановление | `N_failed_started / N_started × 100%`; отдельно `dropped_iterations` (запросы **не были начаты** и не должны маскироваться долей HTTP-ошибок); дальнейшее поведение после снижения нагрузки — отдельная стресс/восстановительная проверка по этапу 6 |

**Семантика успеха:** HTTP 200 недостаточно; для `/io` необходим ожидаемый `scenario=io, payload=OK` после реального ответа эмулятора; для `/cpu` — канонический digest и число итераций `N`. Поэтому не допускается «оптимизация» до возврата заранее захардкоженной строки вместо вычисления/ожидания.

**Время задержки:** для HTTP учитываем полное время по клиенту k6; фиксируем точную версию инструмента и, при необходимости, отдельные сетевые компоненты (DNS/соединение). В документации k6 метрики `http_req_*` помечаются временем **завершения** запроса, что важно при границах измерительного окна — протокол должен это учесть. Контракт k6: [D1], [D2].

**Распределение метрик:** первичная метрика — максимальный подтверждённый устойчивый успешный RPS `C` для `J-VT/J-PT` в I/O-bound сценарии; **p95 и ошибки — обязательные ограничения качества**, контроль генератора и эмулятора — технические условия валидности; остальные показатели — вторичные и диагностические, используемые для ответа на общий RQ, а не для неограниченного поиска «победителя».

## 6. Контролируемые условия и возможные искажающие факторы

| Контролируемый параметр | Что фиксируем | Что произойдёт при нарушении |
|---|---|---|
| **Прикладная работа** | Контракт JSON, алгоритм SHA-256, единый `N`, входные 32 нулевых байта, один исходящий HTTP-вызов `/io` | Нельзя отличить пользу конкурентности от разного объёма работы |
| **Интенсивность и сценарий** | Один k6-скрипт, одинаковые `L1–L3`, тайм-аут, размер ответа, HTTP/1.1, keep-alive | Разные нагрузки/протоколы объясняют разницу сами по себе |
| **Ресурсы SUT** | Те же квоты CPU/RAM, Linux/cgroup v2, одна машина или документированная изоляция | Сравнение сводится к ресурсным бюджетам |
| **Конфигурация JVM** | Те же JDK, GC, heap/флаги, Boot/Tomcat, версия HTTP-клиента; J-PT/J-VT — **одна Java-сборка** | Различия компилятора, GC или Spring могут выглядеть как эффект потоков |

| **Сбор и анализ** | Единые определения k6/cgroup, UTC и `run_id`, неизменённые сырые данные | Потеря исходных наблюдений или неодинаковая обработка даёт ложный эффект |

**Частично/неустранимо контролируемые факторы:** язык и runtime Go, стандартные библиотеки SHA-256, обработка HTTP внутри Spring vs `net/http`, а также разница блокирующего и неблокирующего пути в Kotlin. Эти отличия **не объявляются устранёнными**; они фиксируются и рассматриваются как угроза внутренней/конструктной валидности. В основной паре J-PT/J-VT смешение существенно меньше, но не равно нулю.

**Тест самого стенда — часть научности:** A/A-серии одинаковой конфигурации должны показать приемлемый разброс, а k6/эмулятор — измеренный запас ресурсов. Неотклонение статистического теста A/A **не доказывает эквивалентность**: дополнительно нужно заранее задать допустимый эффект A/A и интервал. Калибровку SHA-256 проводить по независимому эталонному скрипту. Полный протокол — этап 6.

## 8. Критерий практически значимого эффекта и правило принятия вывода

**Согласованное направление (вариант Б):** главным критерием является *увеличение максимального устойчивого успешного RPS при одинаковом качестве обслуживания*, а не снижение p95 на 20% в фиксированной точке. Основной контраст — J-VT/J-PT на I/O. Выигрыш должен быть статистически убедительным **и** превышать заранее согласованный порог `δ_min`.

**Требуют численного закрепления до подтверждающих измерений:**

1. **`T_p95` (мс)** — максимально допустимый p95 среди корректных ответов при измерительной нагрузке. Источник: заданное SLO, либо отдельно обоснованный бюджет относительно внешней задержки ~100 мс + накладные расходы; нельзя выбирать по фактическому победителю.
2. **`E_max` (%)** — максимально допустимая доля ошибок и тайм-аутов среди начатых запросов; `dropped_iterations` k6 фиксируются и разбираются отдельно, как и ошибки/перегрузка эмулятора.
3. **`δ_min` (%)** — минимальный выигрыш J-VT в максимальном устойчивом RPS, который автор заранее считает практически значимым; отдельный критерий от статистической значимости. Число из научных работ напрямую не следует.
4. **`Q_arrival` и правило устойчивости** — технический допуск отклонения достигнутой нагрузки от заданной, число повторов и требуемая доля валидных прогонов, чтобы одна удачная серия не превратилась в «максимум».
5. **План поиска границы** — утверждённое дополнение этапа 6 **только для `J-PT/io` и `J-VT/io`**; вторичные сравнения Kotlin/Go/CPU остаются на `L1–L3`. Фактические RPS и расположение ступеней фиксируются после пилота, до основной серии.

**Почему не перенесли прежние 20% / 5% / 1% автоматически:** 20% относились к p95, который теперь **не** является основной метрикой; порог не может автоматически означать 20% выигрыша RPS. Допуск «потеря успешного RPS не более 5%» также не нужен как самостоятельное правило, когда максимальная устойчивая успешная пропускная способность сама является целевой метрикой, а входная нагрузка и ошибки контролируются. Число 1% может быть рассмотрено как *инженерный кандидат* ограничения ошибок, но не как общепринятый результат статей [A1–A7].

**Отсутствие эксплуатационных SLA/SLO** не означает отсутствия порогов: учебный исследователь вправе установить их заранее как критерии экспериментального сравнения и сообщить, что это **авторские инженерные допущения**, а не стандарт индустрии. До утверждения числовых границ вывод по основной H₁ не формализован окончательно.

**Правило научного вывода:** при валидном стенде, одинаковых ограничениях качества и заранее утверждённой процедуре оценки `C` утверждать H₁ только тогда, когда односторонний интервал для `C_VT/C_PT` лежит выше `1+δ_min`. Если данные не позволяют установить границу или оценить неопределённость, результат обозначать «неопределённо/граница не установлена», а не назначать победителя. Отрицательный результат остаётся научно полезным.

### 8.1. Обоснование согласованных предварительных ориентиров 200 мс / 1% / 15% (не нормативы)

**Порог p95 = 200 мс** — проектный бюджет для I/O-пути с номинальными 100 мс ожидания внешнего эмулятора: условно около 100 мс на ожидание и около 100 мс на сетевые, серверные и очередные задержки. Это **не измеренный** бюджет: реальные p95 низкой нагрузки и вариация задержки эмулятора пока неизвестны, а процентили нельзя строго складывать как независимые постоянные слагаемые. Предельное время имеет смысл лишь после проверки, что оно выше фактически достижимого базового уровня и в нём остаётся запас для ожидаемых очередей. Критерий является исследовательским, а не производственным SLA.

**Предел ошибок = 1%** — учебное условие «не менее 99% начатых запросов завершаются корректно» для каждой допустимой ступени нагрузки, включая тайм-ауты и неверный ответ. Оно не означает, что 1% ошибок — индустриальная норма или что все случаи одинаково приемлемы. На этапе 6 нужно заранее определить статистическую точность оценки доли ошибок, число запросов и правило агрегации по независимым прогонам; при небольшом числе запросов наблюдаемые 0% ещё не подтверждают истинную долю ниже 1%.

**Минимальный эффект δ_min = 15%** — предложенное автором определение *практически интересного* выигрыша по `C_VT/C_PT`, то есть порог отношения `1.15`, а не оценка из рассмотренных публикаций и не статистический уровень значимости. Его можно аргументировать как требование ощутимого преимущества перед сложностью/ресурсными компромиссами альтернативы; однако число 15% остаётся **выбором исследовательской значимости**, а не выводом из данных. По техническому A/A-пилоту проверяется, способен ли эксперимент достаточно точно различить такой эффект; если разброс велик, прежде всего улучшают изоляцию, длительность, число независимых повторов и разрешение сетки RPS, а **не уменьшают порог в ответ на увиденный эффект между моделями**.

### 8.2. В какой момент разрешено уточнять значения

**Этап 3 (принят):** согласованы направленная гипотеза, метрика устойчивой ёмкости, принцип ограничения качества и предварительные ориентиры 200 мс / 1% / 15%; это не результаты измерений и не окончательно откалиброванные пределы.

**Этап 6 ПР3 — проект пилота; при последующей реализации стенда — фактический технический пилот до подтверждающего сравнения:** (а) проверить задержку и стабильность эмулятора, p95 контрольного низконагруженного HTTP-тракта, достаточный запас k6, соединений и CPU; (б) провести A/A и оценить разброс/точность на уровне независимых прогонов; (в) определить диапазон и шаг RPS, чтобы находить **границу устойчивости**, а не только лучшее из трёх грубых значений; (г) проверить длительность окна и мощность сравнения для δ_min. В рамках данной ПР3 стенд лишь проектируется: если он ещё не реализован, этап 6 может зафиксировать только **протокол будущей калибровки**, а не выдавать её параметры за измеренные. Калибровочные результаты нельзя объединять с подтверждающими наблюдениями при последующей проверке H₁. Часть испытаний сверх матрицы 4×2×3 требует отдельного согласования.

**После фактического пилота на реализованном стенде, но до основной серии:** представить обоснованную окончательную тройку `T_p95`, `E_max`, `δ_min` и критерии `Q_arrival`/устойчивости пользователю на согласование; зафиксировать с версиями в `configs/experiment.yaml` и `configs/acceptance.yaml`, включая точное правило расчёта порога и оценки максимума. Допустима поправка 200 мс, если независимая калибровка показала, что такой бюджет физически недостижим или неинформативен, **но не для повышения шансов конкретной модели на победу**. Изменения сопровождаются объяснением, что именно в калибровке их мотивировало.

**После начала подтверждающей серии:** пороги и критерии принятия H₁ уже не менять по увиденным эффектам. Вынужденное изменение означает новый зафиксированный эксперимент; исходную серию нужно сохранить и раскрыть как отдельную. Если H₁ не подтверждается, это корректный научный результат, а не ошибка постановки.

**Проверка потенциальной достижимости:** при номинальном ожидании 100 мс один запрос удерживает примерно 0,1 с времени ожидания, поэтому поток 1000 запросов/с создаёт ориентировочно 100 одновременно ожидающих операций, а 2000 запросов/с — 200 (*порядковая оценка*, не фактическая ёмкость). На таких нагрузках могут проявиться ограничения серверного пула platform threads; одновременно нужно убедиться, что HTTP-клиент, сеть, k6 и эмулятор не ограничивают сравнение раньше SUT. Подбираем **информативную область нагрузки**, а не результат под заранее желаемого победителя.

## 9. Статистика: требования к последующему этапу 6

- **Единица анализа:** независимый измерительный прогон — одна запись RPS, p95, ошибок, CPU/RSS при фиксированной интенсивности; HTTP-запросы внутри прогона не являются независимыми экспериментальными повторениями. При оценке `C` используется повторяемая серия уровней/блоков, а неопределённость рассчитывается с учётом зависимости измерений внутри блока.
- **Повторы:** минимум 5; согласованный проектный план — 10 независимых прогонов на каждую из 24 основных конфигураций. К этим 240 дополнительно проектируются **только** ступени J-PT/io и J-VT/io (ориентир 80–160 прогонов); точная сетка после пилота, до основной серии.
- **Фиксация порогов:** `T_p95`, `E_max`, `δ_min`, `Q_arrival`, правило согласованного окна измерения и критерий допуска нагрузки записать в протокол до основных измерений; калибровка может только обосновывать их выбор до замораживания конфигурации, а не использовать результаты подтверждающего сравнения для подгонки.
- **Рандомизация/статистика:** перемешанный либо блочный порядок запусков по записанному seed; заранее определить оцениватель ёмкости, доверительный интервал отношения `C_VT/C_PT` и метод при дискретной сетке/цензурированной верхней границе; оценить необходимое число блоков по пилотному разбросу. Если честный 95%-й интервал не построить, гипотеза остаётся непроверенной.
- **Ограничения:** не исключать плохие прогоны из-за результатов SUT; технически невалидные серии сохранять с причинами. Превышение p95 или ошибка самого SUT — содержательное наблюдение, помогающее определить границу, а не основание удалить данные.
- **Контроль генератора:** k6 открытой модели, достаточные VU, мониторинг реальной подачи (`actual_started_rps`), `dropped_iterations`, CPU, эмулятор и сеть. Различать «SUT не выдерживает нагрузку» и «k6/эмулятор не может испытать SUT».

### Нужны ли изменения ранее утверждённых решений?

**Согласованная синхронизация 16.11.2026:** четыре модели, два сценария, один Java-артефакт J-PT/J-VT, межплатформенные ограничения и базовая матрица `4×2×3` сохранены. Метод определения `C` зафиксирован только для J-PT/io и J-VT/io в принятом этапе 6; RQ2–RQ4 уточнены как сравнение фиксированных нагрузок. Численные параметры приняты **как проектные** с обязательной проверкой пилотом до подтверждающих измерений; окончательные параметры требуют документированного отдельного согласования. Реального benchmark ещё нет.
