## 5.1. Архитектура стенда

### 5.1.1. Исследуемая система и измерительная цепочка

Стенд состоит из пяти обязательных частей: (1) **SUT** — четыре функционально эквивалентных варианта REST-сервиса; (2) **источник воздействия** — k6; (3) **сбор измерений** — метрики HTTP-клиента нагрузки, метрики JVM/Go и контейнеров, отдельная диагностика; (4) **хранилище** — сырые данные, логи, манифесты и выгрузки временных рядов; (5) **анализ** — Python-скрипты для проверки, агрегирования и сопоставления результатов. Шестой, необходимый для сценария I/O, вспомогательный компонент — **контролируемый внешний HTTP-эмулятор**, который не является исследуемым SUT.

Один измерительный прогон = **один активный вариант SUT**, один сценарий (`/io` либо `/cpu`), один зафиксированный профиль интенсивности. k6 обращается **напрямую** к одному SUT, без общего reverse proxy или балансировщика. Остальные варианты SUT не работают во время этого прогона. В диаграмме четыре исходящие ветки от k6 означают альтернативы, **не одновременную нагрузку**.

**Поток запроса I/O:** k6 → `GET /io` выбранного SUT → HTTP-клиент SUT → `GET /delay` эмулятора → асинхронный таймер задержки на эмуляторе → фиксированный ответ эмулятора → фиксированный ответ SUT → k6. Начальный проектный параметр эмулятора: **100 мс**; это ориентир настройки, не результат научного измерения. База данных не используется.

**Поток запроса CPU:** k6 → `GET /cpu` выбранного SUT → многократный SHA-256 фиксированных данных → проверяемый digest → k6. Эмулятор не вызывается. Целевой порядок времени чистых вычислений **50–100 мс на запрос** — предварительный ориентир; число итераций определяется калибровкой и затем не меняется между вариантами внутри основной серии.

**Поток измерений:** k6 сохраняет исходы HTTP-запросов и временные параметры; Micrometer/Go runtime + cAdvisor экспортируют метрики в Prometheus; для каждого `run_id` выполняется выгрузка соответствующего временного окна в неизменяемые файлы. Аналитический скрипт работает только с сохранёнными данными, а не с графиками интерфейса. JFR и Go pprof используются **в отдельных диагностических сериях**, а не в основных сравнительных прогонах, чтобы не менять нагрузку профилированием.

### 5.1.2. Четыре варианта SUT

| Вариант | Сервер и модель выполнения | Реализация `GET /io` | Реализация `GET /cpu` | Важная оговорка |
|---|---|---|---|---|
| **J-PT** | Java 21, Spring MVC + Tomcat; платформенные потоки обработчиков, ограниченный явно заданный пул | Общий для Java/Kotlin Reactor Netty `WebClient`; синхронное ожидание через `.block()` на потоке обработчика | Одинаковый алгоритм SHA-256 на Java | Базовая точка сравнения JVM |
| **J-VT** | **Тот же Java-артефакт**, Spring MVC + Tomcat; виртуальные потоки обработки запросов, `spring.threads.virtual.enabled=true` и проверка фактического `Thread.isVirtual()` | Тот же клиент и `.block()`, но ожидающий обработчик работает в virtual thread | Тот же Java-код SHA-256 | Отличие J-PT/J-VT свести прежде всего к типу потока и конфигурации сервера; виртуальность подтвердить в runtime |
| **K-CO** | Kotlin, Spring MVC + Tomcat; контроллер `suspend fun` и асинхронное Servlet-возобновление | **Тот же Reactor Netty/WebClient** с `awaitBody`/`awaitSingle` из `kotlinx-coroutines-reactor`, **без `.block()`, `runBlocking` и `Thread.sleep`** | Тот же алгоритм SHA-256 на Kotlin, без бессмысленного `withContext` | Асинхронная обработка и её диспетчер — часть варианта; сравнение не полностью изолирует стоимость корутин |
| **G-GO** | Go `net/http`, обработка входящих соединений с goroutines | Общий `http.Client`/`Transport` с keep-alive и заданными лимитами, ожидание ответа без busy-wait | `crypto/sha256` и тот же алгоритм цепочки | Это **межплатформенный** REST-бенчмарк, не доказательство изолированного эффекта goroutines |

Все три JVM-варианта используют **одну версию JDK 21**, **одну версию Spring Boot**, одинаковый HTTP-сервер Tomcat и общий Reactor Netty HTTP-клиент с одинаково фиксируемыми тайм-аутами, лимитами соединений, размером ответов и keep-alive. Java J-PT/J-VT собираются **из одного исходного проекта и одного бинарного файла**; выбор модели задаётся профилем окружения. Kotlin использует собственную реализацию HTTP-контроллера и приостанавливаемое API клиента; такое различие **обязательно интерпретируется как угроза конструктивной и внутренней валидности**. Реальная поддержка `suspend` в контроллерах Spring MVC подтверждена документацией Spring Framework, но корректное поведение конкретной сборки ещё требуется проверить техническим smoke-тестом [T3].

**Контроль неожиданных блокировок:** для K-CO запускать диагностические серии с записью событий планирования и длительности выполнения, измерять количество активных request-threads и event-loop threads, проверять, что число занятых потоков не растёт линейно со временем ожидания. Для J-VT отдельно проверять реальные virtual threads, JFR-события закрепления (если поддерживаются выбранной JDK), число carrier threads и отсутствие долгих блокировок в обвязке клиента. Сам факт вызова `suspend` или включения свойства Spring ещё не подтверждает правильную модель выполнения.

### 5.1.3. Контракт входов и выходов

- **`GET /io`**: фиксированный JSON-ответ `{"scenario":"io","payload":"OK"}`, HTTP 200, `Content-Type: application/json`. Перед ответом SUT обязан получить от управляемого эмулятора ожидаемый маркер `OK`. При ошибке, тайм-ауте или неожиданном маркере возвращается одинаково определённый код ошибки; ложный успех запрещён. Успех проверяется k6 одновременно по статусу и полям ответа.
- **Эмулятор `GET /delay`**: возвращает детерминированный маркер `OK` с фиксированным payload; ждёт заданный интервал через таймер/средство ожидания, **не через CPU busy-wait**; умеет корректно отменять ожидание при закрытии запроса; имеет `/health` и `/metrics`. Параметр задержки задаётся конфигурацией и записывается в манифест.
- **`GET /cpu`**: используется **ровно 32 нулевых байта (`0x00`)** в `fixtures/cpu_input.bin`, известный SHA-256 входного файла и одинаковое число итераций `N`. Алгоритм: `state = SHA-256(state)` повторить `N` раз, начиная с идентичных байтов; вернуть канонический JSON `{"scenario":"cpu","digest":"<lowercase-hex>","iterations":N}`. Цепочка хеширования должна реально исполняться и проверяться независимым эталонным Python-скриптом; статический предрассчитанный digest как подмена вычисления недопустим.
- **Идентичность результатов:** побайтное соответствие эталонной схеме и значений после нормализации кодировки и порядка полей JSON; список обязательных полей и HTTP-коды одинаковы для всех четырёх SUT. Динамические временные метки и случайные данные не входят в измеряемый payload.
- **Сетевая дисциплина:** HTTP/1.1, повторное использование соединений, отключённое сжатие, одинаковый короткий JSON и HTTP-тайм-аут для всех; точная конфигурация и максимальный размер пула утверждаются после калибровки; лимит должен быть достаточно высок, чтобы случайно не стать скрытым различающим фактором.

### 5.1.4. Измерительный контракт

| Показатель | Источник и единица | Правило получения | Назначение |
|---|---|---|---|
| Успешная пропускная способность **одного прогона** | k6, **корректных HTTP-запросов/с** | Успех = HTTP 200 + правильный JSON/digest после реальной работы; `N_correct/T_measurement` | Промежуточная измеренная метрика, **не максимум `C`** |
| **Подтверждённая устойчивая ёмкость `C`** | анализ независимых прогонов, **корректных запросов/с** | Наибольший подтверждённый устойчивый successful RPS среди проверенных ступеней, выполняющих p95/ошибки/технические критерии; оценка, статус границы и неопределённость определяются этапом 6 | **Первичная метрика этапа 3, вариант Б**, для `/io` сравнить `ρ=C_VT/C_PT` с `1+δ_min` |
| `p50_success`, `p95_success`, `p99_success` | k6 + проверка ответа, **мс** | End-to-end длительность **только успешно завершённых семантически корректных ответов**; одна оценка каждого перцентиля **за прогон**; нужны выделенный Trend/тег и raw | `p95_success ≤ T_p95` — условие качества; длительности ошибок/тайм-аутов сохранять отдельно, не подменять общим `http_req_duration` |
| Ошибки и тайм-ауты | k6, **% / число** | Неправильные ответы (включая HTTP 200 с неверным payload), HTTP-ошибки, тайм-ауты / все начатые запросы; `dropped_iterations` отдельно | `errors_pct ≤ E_max` — условие качества SUT, не обязательно техническая невалидность измерения |
| CPU SUT и CPU генератора | cAdvisor/cgroup, **CPU-секунд/с (эквивалент ядер)** | Разность накопленного CPU-времени в границах одного прогона; отдельно показывать долю от CPU-квоты | Ресурсные затраты и контроль k6 |
| RSS и память контейнера | cAdvisor/cgroup, **MiB** | `container_memory_rss`/эквивалент cgroup v2, пиковое значение; также фиксировать working set как отдельную метрику | Межплатформенно сравнимые ресурсные показатели с описанием определения |
| JVM heap/GC/threads | Micrometer, JMX/JFR (диагностика) | heap MiB, число и длительность сборок, platform/virtual threads | Интерпретация JVM-вариантов; **не считать одинаковой метрикой с heap Go** |
| Go heap/GC/goroutines | Go `runtime/metrics`, `runtime.NumGoroutine()` | MiB, события GC/паузы, число goroutines | Диагностика Go Runtime; не подменять ими сравнение RSS |
| Эмулятор: latency/CPU/in-flight/errors | Эмулятор + cAdvisor | Количество одновременно обслуживаемых запросов, задержка сверх заданного таймера, ошибки | Доказательство, что эмулятор не ограничивает SUT |
| Предложенный/достигнутый RPS | k6, req/s | Конфигурация `constant-arrival-rate` / `ramping-arrival-rate` + фактические старты, `dropped_iterations` | Контроль открытой модели и перегрузки генератора |

**Сборщик и место хранения:** метрики JVM через Spring Boot Actuator + Micrometer `/actuator/prometheus`; Go-метрики и эмулатор через совместимые с Prometheus `/metrics` с едиными метками `variant`, `scenario`, `run_id` (высококардинальные метки — только для локального стенда). Системные метрики — cAdvisor, Prometheus регулярно их опрашивает. Интервал scrape — **предварительно 1 с** (проверить стоимость мониторинга); именно одинаковое окно измерения фиксирует сравнимость. Часы контейнеров одного хоста общие; время запуска записывается в UTC, длительность нагрузки определяется монотонными часами k6. Пропуски метрик и аномалии часовой синхронизации фиксируются и помечают прогон как потенциально невалидный.


**Единый контракт с этапами 3 и 4.** Для каждого `run_id` сохраняются **независимые** `technical_validity` (`valid`/`invalid`) и `quality_pass` (`true`/`false`/`null`), а также причины. При корректно поданной нагрузке превышение p95, ошибки и тайм-ауты SUT означают `quality_pass=false`: это наблюдение для определения границы, **не основание исключать серию**. Технический сбой k6/эмулятора/сбора данных помечает `technical_validity=invalid` и не используется для оценки `C`; при невалидном измерении `quality_pass=null`. Функциональный провал проверки контракта **до измерения** блокирует начало серии.

**Устойчивый RPS и неопределённость.** Из сохранённых `runs.csv` формируются `capacity_estimates.csv` (включая максимальную **подтверждённую** ступень, ближайшую не прошедшую, число независимых повторов, статус `boundary_not_established`, `C` и его доверительные границы при применимости) и `comparisons.csv` (`ρ`, односторонний 95%-й интервал, `δ_min`, решение `supported/not_supported/undetermined/not_testable`). Ориентиры `T_p95=200 мс`, `E_max=1%`, `δ_min=15%` **предварительно приняты** как учебные инженерные ограничения; при отсутствии измеренного пилота не объявляются окончательно откалиброванными. **Согласованный охват (этап 6 v0.3.1):** `C` определяется только для J-PT/io и J-VT/io с помощью дополнительной серии поиска границы; для Kotlin, Go и CPU `capacity_status=not_estimated_by_design`, а выводы ограничены L1–L3. Устойчивая ступень требует ≥9 из 10 технически валидных повторов; односторонняя 95%-я граница отношения `C_VT/C_PT` рассчитывается по принятой проектной процедуре блочного bootstrap (10 000 выборок). Сетка и устойчивость проверяются пилотом; точный физический максимум не утверждается.

**Раздельные режимы запуска.** Технический пилот и A/A перед основной серией используются для выбора/утверждения `configs/experiment.yaml` и `configs/acceptance.yaml`. После заморозки профиля `make reproduce` лишь воспроизводит эксперимент и проверяет пригодность аппаратуры/нагрузки **по уже записанным допускам**; автоматически менять пороги, уровни нагрузки, `N` или ресурсы запрещено.

| Контейнерные ресурсы | **cAdvisor 0.60.6** для cgroup v2 | Планируемый `ghcr.io/google/cadvisor:v0.60.6` (**реальное наличие тега/совместимость проверить**), digest после pull [T8] | Для сопоставимого CPU/RSS без привязки к языку; A4/A6 требуют учёта ресурсов |
| Хранилище временных рядов | **Prometheus 3.15.0**, локальный TSDB | `prom/prometheus:v3.15.0`, digest после pull [T9] | Единое временное окно и экспорт рядов, методика НИР 2; не хранить только агрегаты |
| Анализ | **Python 3.13.17** (интерпретатор проекта), pandas, NumPy, SciPy, matplotlib — **версии будут зафиксированы в `uv.lock`** после построения анализа | `pr3/analysis:<git-sha>`; базовый образ Python 3.13.17 с digest после проверки | A6 — пример открытого REST-артефакта со скриптами анализа; никаких результатов A6 не переносим |
| Оркестрация | **Docker Engine 28.0.4**, **Docker Compose 2.35.1**, Linux x86_64, cgroup v2 | Host tooling, версия заносится в host manifest; `compose.yaml` хранится как код | Контроль ресурсов и повторяемость, аналогично структуре артефакта A6; [T10] |
| Отдельная диагностика | JFR встроен в Temurin JDK 21; Go `net/http/pprof`/`runtime/pprof` из Go 1.27.4 | Функции соответствующих SUT; активируются лишь профилем `diagnostic` | Дополняют наблюдения A4; не должны влиять на основные серии |

**Важное уточнение об образах:** строки `pr3/*:<git-sha>` — **схема будущих локальных имен**, а не существующие registry-образы. Указанные теги внешних образов являются заданиями к будущему `docker pull`; в данной работе **не проверена их загрузка или digest**, что прямо ограничивает текущую степень воспроизводимости. Пакеты Micrometer, Reactor Netty, Tomcat и аналитики не имеют самовольно придуманных версий: фактический полный граф зависимостей фиксируется через lockfiles, а Boot BOM определяет базовую совместимую связку.

### 5.2.1. Привязка решений к принятой литературе

- **[A1] Likuś & Krużel (2025), DOI [10.7148/2025-0555](https://doi.org/10.7148/2025-0555):** релевантен прямому сравнению platform/virtual в REST/Spring и разделению задач с вычислением и ожиданием. У нас **реальное внешнее HTTP-ожидание**, а не только имитация внутри SUT.
- **[A2] Grabowiec, Wiktor & Smołka (2024), DOI [10.35784/jcsi.6353](https://doi.org/10.35784/jcsi.6353):** обосновывает включение Kotlin coroutines и I/O; в реестре отмечено, что **не все модели имели симметричные REST-результаты**, поэтому наш проект отдельно проверяет функциональную и протокольную эквивалентность.
- **[A3] Rosà et al. (2023), DOI [10.1109/APSEC60848.2023.00080](https://doi.org/10.1109/APSEC60848.2023.00080):** вводит ограничения переносимости результатов экспериментальной JVM и необходимость не смешивать конфигурации.
- **[A4] Šimatović et al. (2025), DOI [10.1109/MIPRO65660.2025.11131846](https://doi.org/10.1109/MIPRO65660.2025.11131846):** релевантна контролю GC, CPU и heap и отделению этих показателей от end-to-end RPS.
- **[A5] Soares & Terra (2024), DOI [10.5753/SBLP.2024.3686](https://doi.org/10.5753/SBLP.2024.3686):** пример факторов Go/Java/HTTP-стека; **межплатформенная разница = эффект комплекса факторов**, не изолированной goroutine.
- **[A6] Di Meglio & Starace (2024), DOI [10.1109/ACCESS.2024.3489892](https://doi.org/10.1109/ACCESS.2024.3489892), [Zenodo v2](https://zenodo.org/records/13495203):** ориентир по артефактам, контейнеризации, автоматическому сбору, сырым данным и анализу; архив здесь не запускался.
- **[A7] Sari & David (2026), DOI [10.35870/ijsecs.v6i2.7490](https://doi.org/10.35870/ijsecs.v6i2.7490):** основание контролировать backpressure, насыщение зависимостей и риск OOM в Go, **не доказательство производительности Go REST** (в статье PostgreSQL и пакетная обработка).

**Степень обоснования (уточнено 15.11.2026):** подборка этапа 1 v1.1 и подробная таблица/синтез этапа 2 **уже приняты**; статья A5 имеет подтверждённый GitHub-артефакт. Научные RQ, выбранная метрика `C` и предварительные пороги заданы этапом 3 v0.5.1; эта спецификация не переопределяет их самостоятельно. Ссылки [A1–A7] соответствуют действующим реестру и анализу без смены литературы.

## 5.3. Спецификация окружения

### 5.3.1. Хост и изоляция

**Предлагаемая базовая установка для воспроизводимого запуска (не утверждение о фактическом железе):** отдельный физический компьютер `linux/amd64` (без Docker Desktop/Colima/виртуализации), **не менее 16 логических CPU** и **32 GiB RAM**, локальный SSD ≥100 GiB, Linux с cgroup v2. Конкретные модель CPU, число физических ядер, SMT-топология, Linux distribution/release/kernel, BIOS, governor, frequency, NUMA, Docker storage driver и сведения о фоне снимаются программой `scripts/collect-host-info.sh` до запуска, хранятся в `results/manifests/host.json`. **Версию дистрибутива и ядра заранее не выдумываем**: для окончательной спецификации будет вписано реальное окружение и предоставлен проверенный образ/способ восстановления.

**Предварительное распределение логических CPU при наличии 16 изолируемых CPU (пример, подлежит проверке топологии):**

| Роль | `cpuset` (пример) | `cpus` | `mem_limit` | Замечания |
|---|---|---:|---:|---|
| Только **один** SUT | `0-3` | `4.0` | `4g` | Для JVM одинаково `-Xms2g -Xmx2g`, одинаковый GC и настройки (по умолчанию G1, фактически проверить); Go: `GOMAXPROCS=4`, `GOMEMLIMIT` задавать только после проверки влияния |
| k6 | `4-7` | `4.0` | `4g` | Ресурсы не должны исчерпываться; контролировать CPU и `dropped_iterations` |
| HTTP-эмулятор | `8-11` | `4.0` | `4g` | Мощность проверять отдельной калибровкой; эмулятор не должен стать ограничителем |
| Prometheus / cAdvisor / оркестратор | `12-15` | бюджет внутри группы | отдельные лимиты: Prometheus `2g`, cAdvisor `1g` | Мониторинг не делит выделенные CPU с SUT |

`cpuset=0-3` — **только иллюстративная нумерация**. Перед экспериментом через `lscpu -e` и `/sys/devices/system/cpu/.../thread_siblings_list` проверить, что у логических CPU нет SMT-соседей в другой группе. Если это невозможно — применять отдельные физические машины или повторно зафиксированную схему без ложного утверждения об изоляции. Важны **одинаковые ресурсы SUT для всех четырёх вариантов** и отсутствие конкурирующих SUT.

Рекомендуется отключить обновления/вирусные проверки/активные пользовательские задачи на время измерения, зафиксировать governor и частоту CPU, сверить температуру/троттлинг; при проблемах корректной изоляции — вынести k6 и эмулятор на отдельный хост с фиксированной LAN, зафиксировав сетевую топологию как **новую конфигурацию**, не смешиваемую с основной.

### 5.3.2. Процессные и контейнерные настройки

- **ОС/контейнеры:** Docker Engine **28.0.4** + Compose **2.35.1** (точные версии проекта, реальный хост проверяется перед запуском); cgroup v2, Linux x86_64. На всех вариантах одинаковая политика рестарта и лимиты файловых дескрипторов; без memory swap (при возможности) и без дополнительного CPU overcommit.
- **Java/Kotlin:** одна поставка Temurin JDK **21.0.12+8**; `-Xms2g -Xmx2g`, один выбранный GC, единые `-XX` параметры и `-XX:ActiveProcessorCount=4`, одинаковые charset, timezone UTC, один набор конфигураций Reactor Netty и Tomcat. `spring.threads.virtual.enabled` = `false` (J-PT) или `true` (J-VT); свойство в K-CO = `false`, реальное suspend-исполнение проверить.
- **Go:** Go **1.27.4**, `GOMAXPROCS=4`, настройки HTTP-сервера и `Transport` фиксированы в TOML/YAML; влияние `GOMEMLIMIT` и `GOGC` проверяется до фиксации значения, не смешивать результаты разных настроек.
- **HTTP:** внутренняя выделенная Docker bridge-сеть, стабильное разрешение DNS, без публичных сетевых API, прокси и TLS в базовом профиле; HTTP/1.1, отключить `Accept-Encoding`/автоматическое сжатие (и проверить эффективные заголовки), одинаковые keep-alive и ограничения соединений; тайм-аут HTTP **проектно 2 c** для `/io`, финально выбрать после пилота одинаково для всех.
- **Обслуживание метрик:** `/actuator/prometheus`, `/metrics`, `/health` доступны только сети мониторинга/хоста; секреты отсутствуют, Интернет SUT во время benchmark не нужен. Не включать подробное per-request логирование в основном окне измерений.
- **Профилирование:** запись JFR, расширенные GC logs и Go pprof вне основных прогонов; если часть лёгкой телеметрии остаётся всегда включённой, одинаково включать её во всех сравнимых вариантах.
- **Порядок:** последовательный запуск SUT через отдельные Compose profiles (не конкурируют за CPU); полный stop и проверка отсутствия старого процесса, сброс очередей и ожидание стабилизации перед следующим вариантом.

### 5.3.3. Предотвращение узкого места в генераторе или эмуляторе

**Нельзя считать отсутствие узкого места доказанным только потому, что компонент вынесен в отдельный контейнер.** До основной серии выполнить предварительную проверку на потенциально максимальном входном RPS (точное абсолютное значение будет получено по техническому пилоту в рамках утверждённого этапа 6):

1. **k6:** отдельный запуск на простом эталонном HTTP-сервере / контуре, способном ответить быстрее исследуемых SUT; контролировать CPU, RAM, число активных VU, сетевую пропускную способность, фактический RPS и `dropped_iterations`. При появлении собственной деградации k6 сменить ресурсы/машину либо снизить границу валидного испытания; **прогоны с неосуществлённой нагрузкой не считать честным сравнением**.
2. **Эмулятор:** изолированно прогнать нагрузку с запасом к максимуму предполагаемых SUT (рабочий критерий запаса предложено начать с **2×**, затем подтвердить калибровкой); измерять p95 времени **сверх выставленной задержки**, CPU, in-flight, ошибки, число открытых соединений и очереди. Если его latency или ошибки растут — увеличить его ресурсы/соединения или сделать отдельный хост.
3. **Сеть и пулы:** измерить RTT до эмулятора без ожидания, отсутствие packet loss и saturation; проверить, что лимиты `WebClient/HttpClient.Transport` и к6 не создают ограничения до SUT. Для Java/Kotlin использовать одинаковые лимиты пула; сопоставимость Go — по фактической ёмкости, а не названию библиотеки.
4. **Мониторинг:** оценить изменение p95 и CPU с Prometheus+cAdvisor включёнными/выключенными на контрольном варианте; если влияние велико, снизить интенсивность scrape или явно учесть overhead для каждого варианта. Это **предварительная верификация стенда**, а не заменяет обязательный A/A-тест этапа 6.

## 5.4–5.6. Интерфейс с принятым планом эксперимента (этап 6 v0.3.1)

**Утверждённый проект этапа 6 v0.3.1:** 4 SUT × 2 сценария × 3 уровня RPS = 24 конфигурации; **10 повторений = 240 основных прогонов** (минимум задания — 5), дополнительно только J-PT/io и J-VT/io — 80–160 прогонов; всего **320–400** без технического пилота и A/A. Прогрев **60 с**, окно измерения **180 с**. Правило устойчивости ≥9/10, шаг рядом с границей ≤5%, допуск подачи 1%; для A/A-границ и абсолютных RPS требуется пилот. Архитектурный этап эти значения не переопределяет. Для каждого запуска стенд заранее предоставляет:

- конфигурацию нагрузки (open arrival-rate с фиксируемой фактически достигнутой интенсивностью), `run_id` и seed для порядка прогонов;
- разделение **warm-up** и **measurement**, жёстко исключая прогрев из статистики;
- семантическую проверку `/io` и `/cpu` и машинный статус `valid/invalid + reason`;
- одну запись показателя на **прогон**, не на каждый запрос как независимое наблюдение;
- полный набор сырых данных и экспорт метрик за временное окно, достаточных для дальнейшего A/A, оценки разброса, доверительных интервалов и сравнений.

**Этап 6 уже принят:** см. [`../stage_06/experiment_plan.md`](../stage_06/experiment_plan.md) и [`../stage_06/validity_threats.md`](../stage_06/validity_threats.md). Реестр угроз содержит меры против температурного дрейфа, JVM/Go-смешений, блокировок Kotlin, GC, пулов соединений, генератора и эмулятора. Их практическая проверка относится к будущему пилоту и исполняемому стенду, а не к выполненной ПР3.

## Открытые вопросы и границы готовности

1. **Нужны реальные hardware inventory и digest OCI.** До их получения стенд нельзя назвать воспроизведённым окружением с зафиксированными образами. Параметры CPU/RAM в §5.3 — предлагаемый baseline, который может потребовать изменения при выборе доступного хоста.
2. **Kotlin MVC suspend и Spring HTTP client.** Требуется минимальный тест доказательства неблокирующего ожидания, функциональной эквивалентности, фактических потоков и корректного virtual-thread executors; если обнаружатся ограничения стека, **не** подменять Spring MVC на WebFlux без согласования существенного изменения.
3. **Версии/теги vs digests.** Версии реальных релизов проверены по официальным страницам; названия некоторых контейнерных тегов помечены кандидатами и должны быть реально проверены перед сборкой. Spring Boot 3.5.16 — последняя OSS-версия своей ветки; для исследовательского стенда фиксированность допустима, для промышленной эксплуатации надо дополнительно учитывать обновления безопасности [T1].
4. **Настройки клиента, абсолютные уровни RPS и пригодность порогов.** Этапы 2, 3 и 6 уже утверждены: правило выбора уровней, проектные допуски и статистический метод определены; абсолютные RPS, `N` и численные A/A-границы остаются на будущий технический пилот **до** сравнительной серии. Не утверждать, что 240 прогонов выполнены.
5. **Go отличается не только goroutines.** Сравнения Java J-PT/J-VT дают наиболее контролируемую проверку эффекта выбора потоков; Kotlin и Go — сравнение доступных реализаций/стеков, с самостоятельным анализом угроз.
