## 1. Цель, объект проверки и уровни доказательности

Задача проверяющего — независимо установить: (1) какой именно код и окружение применялись; (2) что сравниваемые REST-сервисы решают одну задачу; (3) что измерения собраны при корректных и сопоставимых условиях; (4) что выводы можно пересчитать из неизменённых исходных данных.

**Состав стенда неизменен относительно принятого этапа 5:**

- **J-PT:** Java 21 / Spring MVC / Tomcat, платформенные потоки; **J-VT:** тот же Java-артефакт и конфигурация Spring с включёнными виртуальными потоками и проверкой реальной модели исполнения;
- **K-CO:** Kotlin / Spring MVC, `suspend` + неблокирующий WebClient `awaitBody` / `awaitSingle` (без скрытого `.block()` в I/O);
- **G-GO:** Go `net/http`, goroutines; **межплатформенный** результат нельзя приписывать только механизму goroutines;
- **`GET /io`:** внешний вызов SUT → `GET /delay` отдельного Go-эмулятора, фиксированный ответ `OK`, проектная задержка ~100 мс до калибровки; **`GET /cpu`:** реальная цепочка SHA-256 для 32 нулевых байтов;
- **Источник воздействия:** k6 в открытой модели `constant-arrival-rate` / `ramping-arrival-rate`; один вариант SUT активен в один момент. Мониторинг: Micrometer / Go runtime, cAdvisor, Prometheus. Анализ: Python из сохранённых файлов.

Терминология — по заданию и ACM Artifact Review and Badging:

| Уровень | Кто проверяет и на чём | Что должно быть доказано | Граница вывода |
|---|---|---|---|
| **Повторяемость** (*repeatability*) | Исполнитель, та же версия кода/стенд/хост, новые независимые запуски | Статистическая стабильность результатов, одинаковые ответы и валидные прогоны | Не означает численно идентичный p95/RPS |
| **Воспроизводимость** (*reproducibility*) | Другой разработчик, **тот же опубликованный артефакт**, те же версии и протокол | Он собирает/запускает систему, получает эталонные ответы и сопоставимые результаты на сравнимой аппаратуре | На другой машине прежде всего проверяются артефакт, корректность и направление/устойчивость выводов; абсолютные RPS могут отличаться |
| **Реплицируемость** (*replicability*) | Другой разработчик **самостоятельно реализует** решение по описанию | Совпадает семантика работы и качественно согласуются наблюдаемые закономерности | Не требует битового совпадения и не сводится к запуску нашего Docker-образа |

Неизменность **артефакта/файлов** проверяется хешами. Точность **результата CPU-алгоритма** проверяется побайтно. Производительность оценивается **статистически по независимым прогонам**; отдельные HTTP-запросы не считаются независимыми экспериментальными повторениями. Это следует из анализа A1–A7, в особенности различия между локальными экспериментами и опубликованными пакетами A5/A6.

Для `uv` предпочтителен `--locked`, чтобы устаревший lock не обновлялся молча.

## 3. Релизный пакет для другого разработчика

### 3.1. Состав публикации

Разработчик получает **один явно указанный релиз**, включающий:

1. Исходный Git-репозиторий по commit SHA и release tag; описание ограничений, лицензию на код/данные, документацию архитектуры и настоящую инструкцию.
2. Исходники всех SUT, `io-emulator`, k6, аналитику, тестовый `fixtures/` и эталонный JSON-контракт; **корневой `README.md` с копируемой инструкцией «одна команда»**, требованиями к ОС/железу, примером запуска и описанием результатов.
3. Dockerfile, `compose.yaml`/profiles, `configs/images.lock` со всеми реально полученными digest, lockfiles инструментов и зависимостей; `Makefile` и скрипты проверки.
4. Инвентаризацию экспериментального хоста и реальный файл конфигурации прогонов. Всякое отклонение от рекомендованного хоста (физическая машина Linux x86_64, проектно ≥16 логических CPU / 32 GiB RAM) логируется; характеристики **не выдаются** за измеренные до инвентаризации.
5. Неизменяемую публикацию raw-прогонов, JSON-манифестов, отдельный список SHA-256, полученные агрегаты, графики и точные команды пересчёта (при появлении реальных результатов в ВКР). Рекомендуется выделить архив данных в versioned release/Zenodo с DOI; ссылка появится только после реальной публикации.
6. Краткий раздел «known issues»: несовпадение языка/runtime между JVM и Go, отличие Kotlin suspend от Java thread model, ограниченность конкретных сценариев, ограничения переносимости производительности.

**Граница контроля:** приложение J-PT и J-VT собирается из одного Java-исходника/бинарного артефакта, а переключение типа потоков — явный конфигурационный параметр. K-CO использует suspend без блокирующей подмены. G-GO сравнивается как другая реализация полного REST-стека. На каждый прогон — **один SUT**, иначе распределение ресурсов уже иное.

### 3.2. Хеши и параметры фиксируемого эталона

Файл `fixtures/cpu_input.bin` уже приложен к **этому этапу** и содержит 32 нулевых байта. Его SHA-256:

```text
66687aadf862bd776c8fc18b8e9f8e20089714856ee233b3902a591d0d5f2925
```

Единый CPU-алгоритм:

```text
state = exactly 32 zero bytes
repeat N times: state = SHA-256(state)  # 32 бинарных байта, НЕ hex-строка
return {"scenario":"cpu","digest":lowercase_hex(state),"iterations":N}
```

`N` устанавливается после предварительной калибровки и записывается **целым положительным числом** в фиксированном экспериментальном конфиге/манифесте; выбранное N одинаково для четырёх вариантов, повторная калибровка **не выполняется между их измерениями**. Требовать только одинаковый hex-ввод или проверять статический заранее вычисленный digest недостаточно для подтверждения реальной CPU-работы: в отдельной диагностике проверяется факт вычислений (профили и время CPU).

I/O-контракт: `GET /io` возвращает HTTP `200` + JSON `{"scenario":"io","payload":"OK"}` только после получения правильного ответа от `GET /delay`. Неуспешный upstream вызов (тайм-аут, неверный маркер, HTTP-ошибка) **не может** выдавать ложный `200 OK`; одинаковая карта ошибок для SUT фиксируется в конфиге/тестах. `Content-Type: application/json`. Порядок полей JSON и несущественные пробелы можно нормализовать; **набор и значения полей** совпадают точно. Сжатие отключено, payload и HTTP-тайм-аут одинаковы.

### 3.3. Структура результатов и пример обязательных полей

Уже согласованный этап 5 задаёт дерево `results/raw/<run_id>/`, `results/manifests/<run_id>.json`, `results/processed/`. Манифест одного **фактического** прогона обязан содержать:

| Группа | Минимальные поля | Пример формата, **не результаты** |

| Идентичность | `schema_version`, `run_id`, `variant`, `scenario`, `load_level`, `repeat_index`, `technical_validity`, `technical_invalid_reasons`, `quality_pass`, `quality_fail_reasons` | `run_id: "<UTC>__J-PT__io__L1__r01"` |
| Код и софт | `git_sha`, `release_tag`, `image_digests` (включая k6/Prometheus/cAdvisor), JDK/Kotlin/Go/Boot/k6 версии, lockfile SHA-256 | строки/digest из релиза, не `"latest"` |
| Хост и изоляция | `host_manifest_sha256`, `os`, `kernel`, `cpu_model`, `logical_cpus`, `cpuset`, `cpus_limit`, `memory_limit_mib`, `cgroup_version`, `network_mode` | реальные значения этого запуска |
| Вход/настройки | `experiment_config_sha256`, `fixture_sha256`, `cpu_iterations`, `emulator_delay_ms`, HTTP pool, timeout, arrival schedule, `seed` | из утверждённого конфига |
| Время | `warmup_start_utc`, `measurement_start_utc`, `measurement_end_utc`, `measurement_seconds`, монотонная длительность | UTC ISO-8601, измерительный интервал отдельно от прогрева |
| Качество нагрузки | `target_arrival_rps`, `actual_started_rps`, `dropped_iterations`, `k6_cpu_cores`, `emulator_extra_p95_ms`, `emulator_errors`, `missing_metrics` | числа из реального прогона; `null` не означает «0» |
| Результаты и файлы | `successful_rps`, `p50_success_ms`, `p95_success_ms`, `p99_success_ms`, `errors_pct`, `sut_cpu_cores`, `sut_rss_peak_mib`, `files` с SHA-256 | только после завершения/валидации |

Значения стадии «планируется» нельзя сохранять как `technical_validity: valid`. **Разделяем два независимых измерения:** `technical_validity=valid/invalid` отвечает за соблюдение протокола (генератор, эмулятор, окно, полнота данных, конфигурация), а `quality_pass=true/false` — за соблюдение самим SUT p95 и порога ошибок **при технически валидной серии**. Ошибки/тайм-ауты SUT и превышение p95 **не являются основанием удалять прогон**; это наблюдение о недопустимости данной нагрузочной ступени. Предэкспериментальный провал функционального контракта предотвращает запуск серии. Технически невалидный прогон сохраняется со своей причиной, **не удаляется из raw** и исключается из статистической оценки ёмкости; корректно измеренный, но `quality_pass=false` входит в оценку границы насыщения. В `results/processed/runs.csv` — одна строка на каждый фактически измеренный прогон, включая технически невалидные с причинами, а не только на удачные. Пересчёт выполняется **из сохранённых raw**, а не из кэшированного графика Prometheus. Подробный единый контракт см. §3.4.


### 3.4. Межэтапный измерительный контракт варианта Б (синхронизация 15.11.2026)

**Первичный результат — ёмкость `C`, не RPS отдельного прогона.** На каждом предварительно определённом уровне входящего потока `λ` k6 измеряет начатые запросы, семантически корректные ответы и задержки. `successful_rps = N_correct / T_measurement` — **внутрипрогонная метрика**; `C` — максимальная **подтверждённая повторными независимыми прогонами** устойчивая успешная пропускная способность, удовлетворяющая порогам качества и технической пригодности. Сравнение для основного RQ1: `ρ = C_VT / C_PT` на `/io`. При этом `H₀: ρ ≤ 1 + δ_min`, `H₁: ρ > 1 + δ_min`; односторонний нижний 95%-й интервал должен лежать выше `1 + δ_min`. `δ_min=15%`, `T_p95=200 мс` и `E_max=1%` — **согласованные предварительные исследовательские ориентиры**, не вычисленные из публикаций и не окончательно откалиброванные нормы.

**Определение задержки:** `p50_success`, `p95_success`, `p99_success` относятся **только к запросам, закончившимся HTTP 200 с правильным JSON и результатом вычисления/ожидания**. Обычный `http_req_duration` k6 без семантической фильтрации может включать ошибки; его нельзя молча использовать как `p95_success`. Для этих значений нужен отдельный Trend/тег корректного ответа и однозначный экспорт из raw, при этом длительности ошибочных ответов и тайм-аутов также сохраняются. Если корректных ответов нет, p95 успешных не определён (`null`), а ступень автоматически `quality_pass=false`. Ошибки: `N_failed_started / N_started × 100%`; `dropped_iterations` — **не начатые** итерации и отдельный контроль генератора.

**Два независимых статуса для каждого прогона:**

| Поле | Значение | Влияние на оценку `C` |
|---|---|---|
| `technical_validity` | `valid` или `invalid`: корректность измерительного окна, k6/эмулятора/сети, наличия raw и обязательных метрик | `invalid` сохраняется с причиной, но не используется для оценки `C`; не подменять этим неудачи SUT |
| `quality_pass` | `true`, `false` или `null` (если технически невалидно): `p95_success ≤ T_p95`, `errors_pct ≤ E_max` и корректная функциональная обработка | `false` при технически валидном прогоне **доказывает недопустимость проверенной ступени**, не является техническим браком; проектное правило устойчивой ступени: не менее 9 из 10 технически валидных независимых прогонов (принятый этап 6 v0.3.1) |

**Выходные данные будущего воспроизводимого релиза:** `runs.csv` — одна строка на каждый измеренный прогон с двумя статусами; `capacity_estimates.csv` — строки `variant,scenario,capacity_status,last_confirmed_successful_rps,first_failed_target_rps,repeat_count,C_estimate,C_ci_low,C_ci_high` (если граница не выявлена, `capacity_status=boundary_not_established`, и нельзя выдавать `C_estimate` за физический максимум); `comparisons.csv` — `scenario,variant_a,variant_b,rho,rho_ci_low_one_sided,delta_min,hypothesis_status`. Значение `hypothesis_status` может быть `supported`, `not_supported`, `undetermined` или `not_testable` — без автоматического объявления победителя. По принятому этапу 6 v0.3.1 для `J-PT/io` и `J-VT/io` проводится дополнительный поиск границы: проектно по 4–8 новых ступеней с 10 повторами, всего **240 + 80–160 = 320–400** измерительных прогонов без пилота/A/A. `capacity_estimates.csv` определяет `C` **только для этих двух условий**; для K-CO, G-GO и CPU — `not_estimated_by_design`. Для вторичных сравнений допускается максимум из фиксированных испытанных L1–L3, но он не называется физическим пределом. Блочный bootstrap (проектно 10 000 выборок) и односторонняя 95%-я граница заданы этапом 6; фактическая работоспособность метода и качество охвата границы проверяются пилотом до основной серии.

**Разделение подготовки и воспроизведения:** пилот и A/A до релиза могут определить оптимальные параметры и критерии, после чего они согласуются и замораживаются в `configs/experiment.yaml` и `configs/acceptance.yaml`; независимая команда `make reproduce` лишь **проверяет** соблюдение зафиксированных допусков, не меняя пороги, уровни RPS, `N` или ресурсы автоматически.

## 4. Сценарий для независимого проверяющего — последовательность команд

### 4.1. Предварительные условия

Проверяющий получает доступ к **будущему** опубликованному репозиторию `pr3-benchmark`, релизному тегу, OCI-образам/архиву и согласованному экспериментальному конфигу. Установлены Git, Bash, `make`, Docker Engine + Compose с подходящими версиями, `sha256sum`, Python 3.13+; Gradle запускается через **репозиторный wrapper**, Go и uv доступны из зафиксированных builder/analysis образов либо с версиями, отражёнными в манифесте. Точная схема независимого запуска — Linux x86_64 + cgroup v2, по возможности без виртуализации и с разделением ресурсов k6/SUT/эмулятора/мониторинга. Сетевые порты для функциональной проверки доступны лишь тестовой сети/localhost.

**Ещё не измеренные параметры будущей реализации (не выдумывать):** `REPO_URL` будущего исполняемого стенда, `RELEASE_TAG`, OCI SHA-256, аппаратные идентификаторы, CPU-итерации `N`, абсолютные RPS `L1–L3`, A/A-границы практической эквивалентности. **Уже приняты проектно:** прогрев 60 с, измерительное окно 180 с, 10 повторов, технический допуск подачи 1%, правило 9/10, поиск границы только для двух Java/I/O конфигураций, шаг рядом с границей ≤5%. Проверка и окончательное закрепление после пилота, до основной серии; изменения отдельно согласуются. Если обязательный параметр отсутствует, `preflight` должен завершаться **ошибкой**, а не выбирать незаметный fallback.

### 4.2. Обязательный «быстрый старт» — одна команда для полного проекта

**Нормативное требование к реализованному репозиторию:** после получения **зафиксированного релиза** на заранее подготовленной совместимой машине разработчик открывает корень проекта и запускает **одну команду**:

```bash
make reproduce
```

Это **не дополнительная команда после ручных `preflight`, `build`, `contract-check` и т. п.**, а **единая точка входа, которая вызывает все эти шаги сама**. Если для воспроизведения опубликованной серии требуется определённый профиль, `make reproduce` берёт его из **поставляемого и закреплённого в релизе** `configs/experiment.yaml` (по умолчанию `reference`); дополнительных переменных, ручной правки YAML и интерактивного ввода быть не должно. Альтернативные профили допускаются для исследований, но команда по умолчанию не должна молча выбирать упрощённый демонстрационный режим.

**В корневом `README.md` обязательно предоставить копируемую минимальную инструкцию:**

```bash
# Единожды получить опубликованный релиз (URL и тег будут реальными в публикации)
git clone --branch <RELEASE_TAG> --depth 1 <REPO_URL> pr3-benchmark
cd pr3-benchmark

# Единственная команда запуска и воспроизведения эксперимента
make reproduce
```

До этих команд пользователь устанавливает только **внешние обязательные средства** (Linux x86_64 с cgroup v2, Docker Engine/Compose, Git и make), требования к правам/доступному месту/CPU/RAM указаны в README. **Это предпосылки**, а не скрытые шаги по ручному запуску контейнеров или установке Gradle/Go/uv на хост: сборка/анализ выполняются через зафиксированные образы/инструменты. Если среда или внешние ресурсы не соответствуют требованиям, команда завершается понятной ошибкой `preflight`, а не частичным «успешным» отчётом. Docker-демон и сеть с доступом к опубликованным образам/их OCI-архивам необходимы; возможность офлайн-запуска и источник образов фиксируются отдельно.

`make reproduce` **обязан автоматически, в строгом порядке**:

1. Проверить релизный Git SHA, хеши fixture, dependency locks, `images.lock`, архитектуру, Docker/cgroup, доступные ресурсы и необходимые файлы `experiment.yaml`/`acceptance.yaml`; записать снимок хоста. **Не подставлять фиктивные значения** при отсутствии утверждённых параметров.
2. Загрузить/собрать **точно закреплённые** образы, создать сеть/тома Docker Compose, поднять эмулятор `/delay`, мониторинг и прочие вспомогательные сервисы; обеспечить readiness. Не требовать ручного `docker compose up`.
3. По очереди запускать **все четыре** SUT (J-PT, J-VT, K-CO, G-GO), проверять `/io` и `/cpu`, корректность SHA-256, контроль отказов upstream и фактическое использование требуемой модели исполнения; при провале контракта **не** переходить к измерению.
4. Запустить утверждённый план эксперимента из этапа 6: фиксированный seed и порядок, для каждого условия — readiness, прогрев **вне измерительного окна**, k6-нагрузка, сбор сырых k6/Prometheus/логов/манифестов, завершение одного SUT перед следующим; контроль ресурсов k6 и эмулятора.
5. Проверить качество каждого прогона, сохранить **включая невалидные** raw и причины; посчитать SHA-256 всех исходных файлов, выполнить Python-агрегирование и статистический анализ из сохранённых данных, сопоставить с **заранее зафиксированными** допусками; не обещать побайтово одинаковый RPS/p95.
6. Сформировать в предсказуемом месте `results/reproduction-report.json` и краткий `results/README.md` (условия, релиз, хеши, `PASS` / `FAIL` / `UNVERIFIED` и причины), `results/processed/runs.csv`, `results/processed/capacity_estimates.csv`, `results/processed/comparisons.csv`, графики и архив результатов; корректно остановить контейнеры даже при ошибке, **не удаляя** raw/логи.

**Дополнительный режим для запуска сервиса вручную (не замена полноценного эксперимента):** `make up VARIANT=J-PT` запускает выбранный SUT и его зависимости для локального просмотра, `make down` останавливает. В отличие от `make reproduce`, режим `up` не формирует научный результат; в основном сравнении одновременно активен **ровно один** SUT. CI может использовать `make reproduce-smoke` для короткой технической проверки, но не выдаёт её за полное воспроизведение.

**Приёмочное испытание требования «одна команда»:** независимый разработчик на чистой совместимой Linux-машине получает фиксированный тег, выполняет `make reproduce` **без промежуточных `make build`, `docker compose up`, ручных правок или запросов значений**, затем проверяет: представлены все четыре варианта и оба сценария, есть raw/манифесты/хеши, `run_id` сквозные, данные агрегированы, отчёт перечисляет статусы и причины. CI на отдельном чистом runner проверяет короткую цепочку `make reproduce-smoke`; полное статистическое испытание — на выделенном benchmark-хосте. До создания стенда данный критерий **НЕ ПРОВЕРЕН**.

Ниже — **расшифровка внутренних шагов**, полезная при отладке или аудитe. Это не список обязательных последовательных действий перед `make reproduce`. Переменные из опубликованной карточки релиза показаны как `<...>` (не настоящие URL или теги).

```bash

В `reproduce-smoke` допускается один короткий измерительный прогон на сценарий/вариант, чтобы проверить соединение и пайплайн, **без проверки H₁**. Параметры полного протокола **проектно утверждены этапом 6 v0.3.1**: матрица 4×2×3, 10 независимых повторов, дополнительный поиск границы только для двух Java/I/O конфигураций.

### 4.3. Функциональная проверка — уже подготовленный скрипт

В дополнение к будущему `make contract-check` приложен **реально запускаемый сейчас** скрипт `verify_contract.py` (только стандартная библиотека Python): он вычисляет эталонный digest независимо от SUT и посылает реальные HTTP-запросы, проверяя статус, `Content-Type`, поля JSON и повторяемость ответа. Он **не** создаёт сервисы или имитирует прохождение нагрузки. Его можно встроить в `scripts/check-contract.sh` будущего стенда.

```bash
# Из каталога stage_04; нужен реально запущенный тестируемый SUT.
# <N_из_фиксированного_конфига> заменить целым положительным N.
python3 verify_contract.py \
  --base-url http://127.0.0.1:8080 \
  --scenario both \
  --iterations <N_из_фиксированного_конфига> \
  --fixture fixtures/cpu_input.bin \
  --repeat 3 \
  --output contract-check.json
# Код 0: JSON status=pass, все checks.ok=true; код 1: fail и причины.
```

Упомянутая проверка **не доказывает** того, что SUT действительно вызвал эмулятор, а CPU-алгоритм не был подменён. Поэтому в `make contract-check` обязательны также: (а) отрицательный тест `/io` с недоступным эмулятором, где успех запрещён; (б) проверка числа исходящих вызовов по счётчику эмулятора/трассе; (в) диагностическая проверка реальной CPU-нагрузки и того, что `N` изменяет количество выполненных итераций; (г) для J-VT реальное значение `Thread.isVirtual()` в обработчике; (д) для K-CO отсутствие `.block()`/`runBlocking`/`Thread.sleep` на I/O-пути и контроль занятых потоков/диспетчера в диагностике. Эти проверки не должны влиять на основную серию измерений.

### 4.4. Детали исполнения `make reproduce` (дополнение к обязательному быстрому старту §4.2)

Последовательность строго фиксирована, чтобы два разработчика не интерпретировали команды по-разному:

1. **Preflight:** сверить release SHA, lockfiles, образы и архитектуру, входные файлы и конфиг. Снять модель CPU, NUMA/SMT, governor, ОС, Docker/cgroup и версии инструментов; обнаружить фоновые процессы и неверные лимиты.
2. **Оркестрация:** поднять мониторинг и эмулятор, убедиться в `/health`; **один** выбранный SUT. Убедиться, что остальные SUT остановлены и что фактический тип потока соответствует варианту.
3. **Только preflight и проверка зафиксированных границ пригодности (НЕ калибровка):** оценить k6 CPU/RAM/VU и `dropped_iterations`, фактический RPS, задержку/ошибки эмулятора и сетевой тракт **относительно заранее утверждённого `configs/acceptance.yaml`**. `make reproduce` не ищет новую максимальную нагрузку, не назначает новые пороги `T_p95`/`E_max`/`δ_min`, не меняет `N` или профили нагрузок. Если уже опубликованный профиль невозможно корректно воспроизвести, выдать `FAIL/UNVERIFIED` с объяснением. Пилотная калибровка, выбор диапазона и A/A для фиксации допусков проводятся отдельным процессом **до** релиза/основной серии; изменение параметров требует новой версионированной конфигурации и согласования.
4. **План и порядок:** загрузить **версионированную** матрицу факторов и уровней с числом независимых повторов, прогревом и измерительным окном (этап 6); воспроизвести порядок из `seed`; журнал порядка сохранить перед запусками.
5. **Каждый прогон:** старт SUT → readiness → прогрев (данные не включать) → измерение в отдельном интервале → остановка SUT → экспорт сырых k6-точек, summary (`handleSummary`), Prometheus-временного окна, логов и метрик эмулятора → запись манифеста и SHA-256 → формальная валидация → следующий run. Измерение времени — монотонными часами k6, границы экспорта — по записанным UTC-меткам.
6. **Валидация без удаления:** отдельно записывать `technical_validity` (неполные окна, сбой k6/эмулятора, пропущенные обязательные данные) и `quality_pass` (p95/ошибки SUT). При корректной подаче нагрузки ошибки HTTP/тайм-ауты/неправильный payload SUT в измерительном окне — **неудачная ступень нагрузки**, а не техническая браковка. При провале проверок контракта **до** серии эксперимент не начинать. Все raw и причины сохранять.
7. **Агрегирование и ёмкость:** на **каждый прогон** считать успешный RPS = корректные HTTP 200 / секунды измерительного окна; p50/p95/p99 — **только для корректных ответов**, отдельно сохранять длительности ошибок/тайм-аутов; CPU SUT и RSS. В `capacity_estimates.csv` оценить по повторным прогонам подтверждённую устойчивую ёмкость `C` или зафиксировать `boundary_not_established`; в `comparisons.csv` — отношение `ρ=C_VT/C_PT`, неопределённость и проверку порога, **не вычисляя максимум по одной точке**. Проектный оцениватель и правила проверки устойчивой границы заданы принятым этапом 6 v0.3.1; результаты и пригодность метода могут быть подтверждены только будущим пилотом. Отдельные HTTP-запросы не считаются независимыми статистическими повторами.
8. **Публикация доказательств:** отчёт проверки, manifest, raw/processed CSV/JSON, конфигурации, точные версии и хеши в версии набора результатов. Любой ручной пересчёт из Excel вне скриптов не считается первичным доказательством.

**Физическая изоляция:** проектное распределение для 16 логических CPU: SUT 4 CPU/4 GiB, k6 4 CPU/4 GiB, эмулятор 4 CPU/4 GiB, мониторинг на оставшихся CPU (лимиты согласно этапу 5); это **пример**, который до измерения проверяется на topology-aware SMT/NUMA. JVM `-Xms2g -Xmx2g`, Go `GOMAXPROCS=4`, проектная задержка эмулятора 100 мс, тайм-аут `/io` проектно 2 с — это исходные параметры дизайна, не измеренные значения и не основание утверждать, что узких мест нет.

## 5. Ожидаемые результаты и допустимые расхождения

| Что сравнивается | Что ожидается | Допустимое расхождение / реакция |
|---|---|---|
| Git SHA, модули/образы, lockfiles, конфигурации, fixture SHA-256 | Строго те же ссылки на содержимое | **0 несовпадений**; любое изменение = новый релиз или `FAIL` |
| API: `/io` и `/cpu`, HTTP-коды, `Content-Type`, обязательные поля, digest | Идентичная семантика и успешный JSON всех четырёх SUT | **0 ошибочных ответов** в позитивной функциональной проверке; формат JSON можно сравнивать после каноникализации порядка полей |
| Отказ эмулятора | `/io` не выдаёт ложный успешный ответ | **0 ложных `200`**, иначе `FAIL` |
| Состав прогонов и трассировка | Один SUT на прогон, каждый run_id связан с release/config/seed, warm-up исключён | **0 безымянных или неаудируемых** прогонов; браковка сохраняется с причиной |
| Отсутствие искажений генератором/эмулятором | k6 не исчерпывает CPU/VU, нет пропусков старта, эмулятор не увеличивает ожидаемую задержку из-за очереди | Технические пороги из **отдельной пилотной калибровки** (`configs/acceptance.yaml`, утверждаются этапом 6); до калибровки статус не `PASS`, а `UNVERIFIED` |
| Данные/метрики, экспорт во временном окне | Все обязательные сырые файлы, корректные счётчики и временные границы | **0 отсутствующих обязательных полей/хешей**; допуски для пропусков временного ряда — только если явно утверждены и обоснованы |
| Latency p95/p99, successful RPS, CPU, RSS на **том же** контрольном хосте | Сопоставимое распределение **между независимыми прогонами**, а не одинаковое число | Для метрики `m` граница `Δ_m` **предварительно** определяется на независимых A/A-прогонах и фиксируется в `acceptance.yaml` *до* повторной проверки; правило: `|median(m_new) − median(m_ref)| ≤ Δ_m` + отчёт об интервалах и количестве валидных повторов. Без утверждённого `Δ_m` — `UNVERIFIED`, а не произвольные ±5/10% |
| Производительность на **другом** хосте | Функциональная проверка, качество измерения, выводы с учётом среды; абсолютные числа могут быть другими | **Нет универсального числового допуска RPS/p95**; зафиксировать железо и сравнивать направление/размер эффекта и интервалы по заранее принятому критерию этапа 3 и анализу этапа 6 |
| Полный статистический вывод | Достоверное число независимых прогонов, скрипт расчёта эффектов и интервалов | Согласованный размер эффекта/метод анализа устанавливаются этапами 3/6; нельзя объявлять подтверждение H₁ только по прохождению smoke |

**Порядок фиксации `Δ_m`:** пилот A/A выполняется на неизменной конфигурации, равномерно охватывая разные моменты времени; рассчитывается разброс между независимыми прогонами, отдельно оценивается неопределённость измерения, формируется граница практической эквивалентности и публикуется **вместе с пилотными данными** до сравнения проверяющего. Порог нельзя подгонять по уже увиденным значениям нового прогона. Для независимой репликации на другой аппаратуре критерий трактуется относительно нового базового уровня, а не как требование воспроизвести прежний абсолютный RPS. На момент этапа 4 **числового `Δ_m` нет**, потому что стенд ещё не измерен; его нельзя научно обосновать фиктивными данными.

## 6. Контроль качества и действия при расхождении

| Ситуация | Действие проверяющего | Как фиксируется |
|---|---|---|
| Изменился digest/lockfile, другой Git SHA, подмена данных | Немедленно остановить сравнение; уточнить релиз или зафиксировать новый артефакт | `preflight=FAIL`; отчет со списком несовпадений |
| Один из SUT даёт другой JSON/digest | Не запускать сравнение производительности; исправлять **одновременно и явно** с новой версией всех затронутых артефактов | `contract-check=FAIL`, образец несовпадающего ответа |
| J-VT фактически обрабатывает запросы платформенными потоками; K-CO блокирует диспетчер | **До серии** — функциональный/архитектурный контракт не выполнен, не начинать benchmark; внутри серии фиксировать инцидент и `technical_validity` | диагностический журнал и причина остановки |
| k6 показывает `dropped_iterations`, CPU saturation или не обеспечивает входящую интенсивность | Проверить, не является ли ограничителем **генератор**, и не приписывать его недостатки SUT; тайм-ауты **самого SUT** при технически корректном k6 классифицировать как `quality_pass=false` | логи k6, CPU, фактический started RPS, `technical_validity` отдельно от `quality_pass` |
| Эмулятор насыщается или network RTT дрейфует | Повторить отдельно калибровку; не менять конфиг внутри серии | emulator CPU, in-flight, p95 сверх ожидаемой задержки, host/network manifest |
| Нет Prometheus-окна, сбой временных меток или неполный raw | Сохранить артефакты, браковать и повторить конфигурацию с **новым run_id** | `technical_validity=invalid` + причина + ссылка на новый прогон |
| Измерения на другой ОС/CPU/JDK | Рассматривать как **новый профиль**, сравнивать с учётом среды, не смешивать в одной статистической выборке | новый `host_manifest` и профиль; явное ограничение внешней валидности |
| Направление эффекта расходится с опубликованным | В первую очередь проверить качество и дизайн; затем сообщить несовпадение как научный результат, а не скрывать его | сводные оценки, доверительные интервалы, описание отклонения от протокола |

## 7. Независимая проверка в CI

**Два независимых режима:**

- **CI / pull request:** проверить синтаксис конфигураций/диаграммы, SHA fixture, lockfiles, Java/Kotlin `test`, Go `test`, сборку образов, функциональные `/io`/`/cpu` контракты на кратком запуске, неверный upstream, сохранение схемы manifest и корректную обработку ошибки валидатора. Этот режим предназначен для *логики и целостности*, а не для сравнения производительности.
- **Benchmark / закреплённый физический хост:** только зафиксированное аппаратное окружение и выделенные CPU, опубликованный тег, полный план этапа 6 с независимыми повторениями, анализом/A/A и отдельным release артефактом. Не полагаться на разделяемые CI runners для абсолютного RPS/latency. Если CI smoke проходит, это не значит, что статистический вывод экспериментально подтверждён.

Отчёты CI должны содержать ссылки на commit SHA, контрольные суммы и тестовые логи. GitHub Actions/GitLab jobs также должны использовать фиксированные версии (в идеале полные commit SHAs actions) и минимальные разрешения. Публиковать релизные raw-файлы можно только после проверки, что в них нет секретов/токенов/персональных данных.

## 8. Трассируемость к научным публикациям и принятому проекту

- **A1 — Likuś, Krużel (2025), DOI 10.7148/2025-0555:** прямой REST/Spring benchmark с зависимостью от профиля и интенсивности, но только два повторения и неполный контроль среды. В нашем протоколе отдельные повторы, контроль k6/сети и запись условий обязательны.
- **A2 — Grabowiec et al. (2024), DOI 10.35784/jcsi.6353:** неполное REST-сравнение virtual threads из-за ограничений клиента; для нас необходимо проверять фактическую эквивалентность HTTP-клиента и реальное suspend-ожидание.
- **A3/A4 — Rosà et al. (2023), DOI 10.1109/APSEC60848.2023.00080; Šimatović et al. (2025), DOI 10.1109/MIPRO65660.2025.11131846:** версии runtime/GC и конфигурация среды должны быть зафиксированы, диагностические показатели JVM не заменяют end-to-end latency.
- **A5 — Soares, Terra (2024), DOI 10.5753/SBLP.2024.3686, https://github.com/PqES/2024_sblp:** пример опубликованных кода/данных/скриптов анализа с ограниченной фиксацией окружения и межплатформенными смешениями факторов. В нашем проекте дополняем их pinned OCI и host-манифестом; **Go не трактуется как изолированный эффект goroutines**.
- **A6 — Di Meglio, Starace (2024), DOI 10.1109/ACCESS.2024.3489892, https://zenodo.org/records/13495203:** положительный образец опубликованного replication package с Docker, сценариями нагрузки, сырыми данными и анализом. Наличие архива **не** равно подтверждённому независимому запуску; для нас добавлены машинные gate-условия и проверка хешей.
- **A7 — Sari, David (2026), DOI 10.35870/ijsecs.v6i2.7490:** полезна для требования контролировать backpressure/OOM при I/O; это не REST-бенчмарк. В нашем стенде PostgreSQL отсутствует, а зависимость эмулируется отдельным HTTP-сервисом.

**Источники нормативных технических операций:** Gradle dependency locking — https://docs.gradle.org/current/userguide/dependency_locking.html ; Go modules/checksum — https://go.dev/ref/mod ; uv lock/sync — https://docs.astral.sh/uv/concepts/projects/sync/ ; k6 granular JSON output — https://grafana.com/docs/k6/latest/results-output/real-time/json/ ; k6 summary и рекомендации по `handleSummary` — https://grafana.com/docs/k6/latest/using-k6/k6-options/reference/ . Проектные версии компонентов и сетевую архитектуру см. в **принятом этапе 5, разделы 5.1–5.3**.

### Что сделать при реализации стенда, чтобы протокол стал исполнимым end-to-end

1. Реализовать в **будущем** `pr3-benchmark/Makefile` команду **`make reproduce` как самодостаточный end-to-end запуск** со встроенными этапами §4.2 и всеми диагностическими целями §4.2.1, корневой `README.md` с «Быстрым стартом», а также `make up VARIANT=...` / `make down` для ручной локальной проверки. Добавить `scripts/check-contract.sh` на основе `verify_contract.py` и негативные проверки.
2. Создать настоящие `gradle.lockfile`, `go.mod`/`go.sum`, `uv.lock`; зафиксировать Docker digest/OCI-архивы и версии, затем заменить `<...>` релизными значениями. Проверить наличие всех ожидаемых файлов.
3. Внедрить `run_id`, machine-readable status, SHA-256 raw, UTC-границы, manifest schema и строгий валидатор. Провести техническую проверку k6/эмулятора и нагрузочных очередей.
4. Перенести **утверждённые** параметры из этапов 3/6 в версионированный `experiment.yaml` и `acceptance.yaml`. Отдельно выполнить A/A и заморозить `Δ_m` перед независимым воспроизведением. **Принимать функцию «одна команда» только после независимого прогона с чистого релиза без ручной сборки, настройки и запуска компонентов.**

**Вывод:** другой разработчик сможет проверить правильность программной постановки, неизменность экспериментального артефакта и путь от сырых данных к заключениям. После реализации стенда и согласования этапа 6 тот же протокол станет инструкцией для фактической проверки производительности без ручного вмешательства в код. На данном этапе **запуск четырёх сервисов, получение docker digest и бенчмарков не утверждаются как состоявшиеся**.
