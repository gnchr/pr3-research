## 1. Что проверяем — связь с этапами 1–5

**Основной подтверждающий вопрос RQ1:** превосходит ли J-VT (тот же Java/Spring-артефакт с virtual threads) J-PT (platform threads) по **максимальной устойчивой успешной пропускной способности** `C` при I/O-bound нагрузке `/io` и одинаковых ограничениях качества? Вторичные RQ2–RQ4: **в ограниченном дизайне** сравнить K-CO и G-GO с JVM-вариантами **на одинаковых фиксированных нагрузках L1–L3** и проверить зависимость от I/O-/CPU-профиля; вопросы о максимальных ёмкостях всех четырёх SUT здесь полностью не закрываются. Go характеризует **полный Go/net/http-стек**, а не изолированный выигрыш goroutines.

- **Основная метрика подтверждающего сравнения:** `C_v,io` **только для `v ∈ {J-PT, J-VT}`** — максимальная *подтверждённая в испытанной сетке* устойчивая успешная пропускная способность (корректных ответов/с). Не смешивать `C` с успешным RPS одной ступени. **Для K-CO, G-GO и любого `/cpu`** основными выходами остаются p95, успешный RPS, ошибки и ресурсы на фиксированных `L1–L3`; максимальная устойчивая ёмкость для них **не оценивается**.
- **Основная проверка:** `ρ = C_{J-VT,io}/C_{J-PT,io}` при `C_{J-PT,io} > 0`; `H₀: ρ ≤ 1 + δ_min`; `H₁: ρ > 1 + δ_min`. Для подтверждения требуется **односторонняя нижняя 95%-я граница интервала для ρ > 1 + δ_min**, надлежащий контроль калибровки и установленная граница устойчивости у обеих реализаций. Отсутствие такого результата **не доказывает H₀**.
- **Принятые предварительные ориентиры** из этапа 3: `T_p95,io = 200 мс`, `E_max = 1%`, `δ_min = 15%` (сравниваем с `ρ > 1.15`). Это не SLA и не универсальные значения из статей A1–A7. Для CPU-сценария предлагается **первоначально тот же** `T_p95,cpu = 200 мс` ради единого способа оценки; его применимость нужно отдельно проверить на пилоте. Эти значения **нельзя менять по результатам подтверждающего сравнения**.
- **SUT:** J-PT, J-VT, K-CO, G-GO. `/io`: ровно один HTTP-запрос к изолированному `GET /delay` с номинальными 100 мс неблокирующего ожидания; `/cpu`: последовательная цепочка `state = SHA-256(state)` над 32 нулевыми байтами, один `N` для всех, проверяемый hex digest. Один активный SUT на прогон. Java J-PT и J-VT — **одна сборка**; одинаковые квоты CPU/RAM, HTTP-контракты, сетевые условия.

**Согласование с этапом 3 v0.5:** по прямому разрешению пользователя общая формулировка и RQ2–RQ4 синхронизированы с облегчённым дизайном. `C` оценивается лишь для основного RQ1 (`J-PT/io` против `J-VT/io`); RQ2–RQ4 **по определению** сравнивают p95, успешный RPS, ошибки и CPU/RAM на общих `L1–L3`, без заявлений о максимальной ёмкости Kotlin/Go/CPU. Это ограничение отражается и в итоговом отчёте.

**Следствие литературы (не источник численных норм):** A1/A3 мотивируют смену нагрузочных режимов и сравнение thread models; A2 требует исключить скрытое блокирование Kotlin; A4 — фиксировать GC/JIT; A5/A6 — факторность, повторения и доступность исходных данных; A7 — контроль перегрузки/отказов. Анализ числа повторений и ошибок измерения — утверждённый этап 2 § «Повторения, статистическая обработка и воспроизводимость».

**Согласованное проектное правило определения L1–L3 в независимом техническом пилоте:** оценить устойчивый порог `λ_ref,s` на **одном заранее выбранном контрольном J-PT** отдельно для `/io` и `/cpu`; затем получить три общих для четырёх реализаций уровня: `L1 = round(0.20·λ_ref,s)`, `L2 = round(0.60·λ_ref,s)`, `L3 = round(1.00·λ_ref,s)` в запросах/с с проверкой строгого возрастания и округлением по предварительно утверждённому правилу. **Коэффициенты 0.20/0.60/1.00 приняты как проектное правило, не как результаты измерений или вывод литературы.** Контрольную J-PT выбираем до просмотра сравнительных результатов; полученные уровни после пилота замораживаются для всех четырёх моделей. Если `λ_ref,s` надёжно не определяется, пилот продолжается по заранее описанному алгоритму; произвольных RPS не назначать.

**Ограничение:** эти 24 точки дают срез задержки/успешного RPS/CPU/RSS, **но могут не установить максимум `C`**. Даже если L3 выдерживается J-VT, нельзя объявить L3 его физическим пределом. **Согласовано отдельным решением пользователя:** поиск границы (§3) добавляем лишь для двух I/O-условий `J-PT/io` и `J-VT/io`. Для остальных шести пар «модель × сценарий» вывод ограничивается фиксированными L1–L3, а заявления об их максимальной ёмкости запрещены.

## 3. Дополнительная серия поиска границы устойчивого RPS (ОБЪЁМ СОГЛАСОВАН: только J-PT/J-VT на I/O)

**Почему без неё нельзя считать RQ1 полностью проверенным:** первичная `C` — это граница пригодной нагрузки, а три заранее заданные точки не гарантируют перехода от проходящей ступени к непроходящей. По **явно согласованному пользователем варианту Б** оставляем 240 базовых прогонов без замены и проектируем дополнительную **фиксированную** нагрузочную сетку **только для `J-PT/io` и `J-VT/io`**. Это два сочетания из восьми, которые непосредственно нужны для H₁. Для Kotlin, Go и CPU-сценария **не проводим дополнительный поиск границ** и **не делаем заявлений об их максимальном устойчивом RPS**. Это осознанное ограничение объёма, а не доказательство отсутствия преимуществ у других моделей.

### 3.1. Двухфазный алгоритм — без подгонки под подтверждающие результаты

1. **Технический/поисковый пилот:** на фиксированном железе проверить запас k6 и эмулятора; **только для `J-PT/io` и `J-VT/io`** ступенчато увеличивать `λ` до появления технически корректного, но не выдержавшего качество режима. Отметить интервал `(λ_pass, λ_fail]` для каждой из двух реализаций. Для четырёх SUT и обоих сценариев остаются обычные технические проверки и калибровка L1–L3, **но не поиск максимальной ёмкости**. Пилотные наблюдения не включать в итоговый тест H₁. Сетка определяется алгоритмически и архивируется с SHA и признаком `pilot`.
2. **Формирование фиксированной сетки:** из пилотных интервалов `J-PT/io` и `J-VT/io` выбрать для подтверждения точки около границы так, чтобы соседние уровни различались **проектно не более чем на 5%** и для каждой модели были точки ниже и выше ожидаемой границы. Начальный рабочий ориентир — **4–8 дополнительных уникальных ступеней на каждую из этих двух моделей**. Конкретные RPS, диапазон и верхний потолок определяются *до* подтверждающей серии, с сохранением сетки в `experiment.yaml`. Если для охвата границы требуется более 8 дополнительных ступеней на модель, **сначала отдельно согласовать увеличение бюджета**, а не молча расширять серию. Совпадающие с L1–L3 точки учитываются один раз, без двойного учёта. **Никаких дополнительных ступеней для K-CO, G-GO и `/cpu` не планируем.**
3. **Независимая подтверждающая серия:** на каждой новой уникальной точке двух сеток (`J-PT/io`, `J-VT/io`) выполнить **10 новых независимых прогонов**, объединяемых с базовыми 10 блоками (по одному прогону уровня в каждом блоке). Пилотные данные не использовать повторно. Нагрузку **не расширять адаптивно после просмотра сравнительных эффектов**, чтобы не менять подтверждающий план. Если сетка не охватывает переход «pass → fail», сообщить `boundary_not_established`, не экстраполировать.
4. **Консервативный учёт дискретности:** установить последнюю подтверждённую проходящую и первую более высокую непроходящую ступень, обе в `target_rps`. Отчётливо различать `C_estimate` в **успешных RPS** и интервал сетки в **предложенных RPS**. Для тонкого вывода о 15% учитываем нижнюю и верхнюю границы интервала ступеней, не делаем вывод по округлённой разнице 15%.

**Бюджет согласованного по охвату расширения:** если каждая из двух I/O-реализаций получает `m` новых уникальных ступеней и на каждой выполняется 10 повторов, дополнительно потребуется `2 × m × 10 = 20m` прогонов. При **4** ступенях на модель это **+80**, всего **320**; при **8** — **+160**, всего **400** (без пилота, A/A, повторов технически невалидных запусков). При разном числе ступеней `m_PT`, `m_VT` точная формула: **`240 + 10·(m_PT + m_VT)`**. **Объём поиска и проектное правило 9/10 согласованы; конкретные RPS и значения `m_PT/m_VT` уточняются после пилота до M с отдельной фиксацией.** Если предложенного лимита 4–8 ступеней недостаточно для охвата перехода хотя бы у одной Java-реализации, не экстраполировать максимум и не заявлять подтверждение H₁; расширение выше согласованного диапазона требует нового согласования.

### 3.2. Устойчивость и оцениватель C

**Только для `v ∈ {J-PT, J-VT}`, `s=io`** на каждой подтверждающей ступени из 10 технически валидных прогонов вычислить `quality_pass` (см. §5). На всех прочих базовых `L1–L3` `quality_pass` тоже сохраняется, но `C` по ним не оценивается. **Согласованный проектный критерий повторяемого прохождения — не менее 9 из 10** независимых прогонов одновременно соблюдают `T_p95`, `E_max`, условия подачи и стационарности; пригодность этого правила проверяется пилотом, а изменение до M требует отдельного согласования. При технической браковке запуск **заменяется новым прогоном с новым run_id**, а исходный raw сохраняется; отказ самого SUT не является браковкой.

`λ*_{v,io}` для `v ∈ {J-PT, J-VT}` = **наибольшая испытанная и подтверждённая** интенсивность, для которой соблюдён критерий 9/10, причём все исследованные меньшие ступени в окрестности границы имеют непротиворечивый статус. Если соседние ступени противоречат предполагаемой монотонности, отметить `nonmonotone/ambiguous` и не назначать единственную точную границу без заранее описанного повторного дизайна. `C_estimate(v,io) = median(successful_rps_i at λ* across technically valid runs)` (проектное определение; следует подтвердить в предрегистрации), а `λ_fail` — первая вышележащая подтверждённая ступень, не прошедшая критерий. Если ни одна точка не прошла, `below_range`; если нет непроходящей выше — `boundary_not_established` и **тест H₁ по отношению ёмкостей не считается определённым**. Для K-CO, G-GO и всех CPU-условий значение `capacity_status=not_estimated_by_design`; любые численные «максимумы» для них запрещены.

**Не путать:** `λ*` (предложенная интенсивность входящего потока) и `C` (действительно **корректно обслуженный** успешный RPS). В условиях `E≤1%` они близки, но не тождественны. Нельзя приписывать SUT чужие сбои эмулятора и нельзя получать искусственное улучшение `p95_success`, отбрасывая ошибки/тайм-ауты: они учитываются в обязательном `E_max`.

## 5. Детерминированный протокол отдельного измерительного прогона

### 5.1. Продолжительность и запуск

**Согласованный проектный режим** на каждую `(variant,scenario,λ,repeat)` (возможна документированная корректировка после пилота до M):

- Создать новый `run_id`, проверить образ, конфиг, ресурсные лимиты, остановить другие SUT, перезапустить активный SUT и обеспечить готовность, начальное состояние эмулятора/пулов/мониторинга. Прогреть **60 с**, данные прогрева не включать в основное окно.
- Включить отдельный **180-секундный** измерительный интервал на постоянной целевой интенсивности `λ` через k6 `constant-arrival-rate`, `timeUnit=1s`; одна итерация — **один** HTTP GET, без `sleep()` и без выполнения дополнительных запросов к SUT. `preAllocatedVUs`/`maxVUs` выставлять из предварительной независимой калибровки с запасом и **одинаковым правилом** между вариантами. Согласованные проектные 60/180 с проверяются пилотом на стационарность JVM JIT, GC, сетевые колебания и достаточность запросов для оценки 1% ошибки.
- После окончания подачи дать **не менее 5 с** `gracefulStop`, если HTTP-тайм-аут не больше проектных 2 с, и сохранить также прерванные/тайм-аутные запросы; не замещать пропуски нулями. Конкретное правило окна определяется **по времени старта** запроса: для прогона учитываются запросы, запущенные в `[t0,t0+180с)`, даже если их ответ получен во время drain; они должны завершиться либо зафиксированным тайм-аутом. k6 стандартные точки `http_req_*` помечаются временем *окончания* запроса, поэтому нужен сквозной request_id/start timestamp в сыром журнале, **а не только фильтр готового HTTP-summary по timestamp**.
- Считать `successful_rps = N_correct_started_in_window / 180с`, `actual_started_rps = N_started_in_window / 180с`, `error_pct = 100·N_failed_started/N_started`. `N_started = N_correct + N_failed` после учёта тайм-аутов; ожидаемые, но не начатые итерации считать в `dropped_iterations` **отдельно**. Исключения и «зависшие» неучтённые исходы запрещены; несоответствие когорты/счётчиков — технический дефект.
- Для I/O отдельно записывать p95 задержки эмулятора и количество его незавершённых upstream-запросов; для CPU — эталонный SHA/digest и `N`. Собирать CPU `CPU-секунд/с`, RSS/peak MiB, тайм-ауты, системные потоки, основные JVM/Go-метрики; тяжёлое профилирование только в D.

**Размеры прогона для планирования, не результат:** 240 × (60+180) секунд = **16 часов** чистого прогрева/измерения без restart/healthcheck и задержек между прогонами; для 320 прогонов — **≈21,3 часа**, для 400 — **≈26,7 часа**. Пилот, A/A, завершения, повтор технических браков и перенос между контейнерами добавляют время. Это показывает ресурсную цену облегчённой серии: её **охват уже согласован**, а точное число ступеней и длительности ещё проверяются пилотом.

### 5.2. Техническая валидность ≠ качество обслуживания

| Поле | Значение и правило |
|---|---|
| `technical_validity=valid/invalid` | Проверены версия/конфиг/fixture, полный измерительный cohort и raw, здоровье k6/сети/эмулятора, верные метки UTC/monotonic, мониторинг CPU/RSS, отсутствие внешней интерференции. Результат SUT, даже с большим p95 и ошибками, **не делает** валидный прогон технически невалидным |
| `quality_pass=true/false/null` | Для **технически валидного** прогона `p95_success ≤ T_p95,s` **и** `error_pct ≤ E_max` **и** корректное достижение заданной нагрузки/отсутствие подтверждённого SUT-induced недопуска и отсутствие систематического накопления очереди по заранее закреплённому правилу. При `technical_validity=invalid` → `null` |
| `capacity_status` | `bracketed`, `below_range`, `boundary_not_established`, `nonmonotone/ambiguous`, `insufficient_valid_runs` — независимо от статуса отдельной точки |

**Технические допуски для P1/P2 (проектные исследовательские, не эксплуатационные нормы):** генератор и эмулятор должны иметь запас CPU/RAM; ориентир CPU ниже 70% выделенной квоты, отсутствие собственных ошибок, отсутствие VU-лимита как причинного ограничения и достаточная пропускная способность связи. Заданный/фактический стартовый RPS должен отличаться **не более чем на 1%** и `dropped_iterations=0` в допустимой ступени (здесь «1%» — новый *технический* допуск подачи, не предел ошибок SUT). Если генератор насыщен или неправильно сконфигурирован — `technical_validity=invalid`. Если **здоровый генератор** не может подавать нагрузку из-за резкого роста времени выполнения запросов SUT, несостоявшиеся итерации **не маскировать браковкой**: отметить `quality_pass=false`, `sut_overload`, сохранить raw. Если невозможно надёжно установить источник падения подачи, статус `unattributed` → `technical_validity=invalid` с обязательным техническим разбором, а не объявлением выигрыша другого варианта. Правила `queue_drift`/`emulator_extra_p95_ms`, `Q_arrival` уточняются **только на P1/P2**.

### 5.3. Как считаем p95 и обрабатываем ошибки

- `p50_success`, `p95_success`, `p99_success` считать **из корректных HTTP 200 + правильного JSON**, с тегом/отдельным Trend для семантически успешных ответов. Ошибки, тайм-ауты и их длительности хранить отдельным raw-каналом. При `N_correct=0`: `p95_success = null`, `quality_pass=false`. Стандартный k6 `http_req_duration` без семантической фильтрации не тождественен `p95_success`.
- **Точность определения времени:** k6 `Response.timings.duration` — длительность отправки, ожидания и получения HTTP-ответа, **не включает** DNS, ожидание свободного подключения и TCP/TLS handshake. В принятых этапах «end-to-end клиентская HTTP-задержка» трактуется как эта стандартизованная k6 HTTP-метрика при общем профиле HTTP/1.1 keep-alive; отдельно сохранять `http_req_blocked/connecting` и при необходимости клиентское полное wall-time как диагностику. Если потребуется **сменить первичное определение p95 на wall-clock включая соединение**, это будет явным методологическим уточнением этапов 3–5, а не неявной подменой в коде.
- `http_req_failed` (из k6) не заменяет проверку **правильного** payload: считать неудачей не только HTTP 4xx/5xx/timeout, но и неверный JSON/digest. `dropped_iterations` — не начавшиеся запросы и контроль качества генерации. Конфигурация ожидания и клиента одинаковая по возможности, timeout `/io` проектно 2 с, а `/cpu` — по утверждённому общему контракту.
- `p95_success`/`errors_pct` за **весь стационарный интервал**; отдельно первые/последние трети и временной ряд хвостовой задержки/инфлайт-очередей. В P1 установить допуск на нарастание очереди, одинаковый для всех моделей; среднее по окну не должно скрывать деградацию в его конце.

## 6. Рандомизация, независимость и защита от дрейфа

**Один статистический блок** объединяет один новый независимый прогон каждого условия базовой матрицы. Проектно `B1–B10`: внутри каждого блока — 24 уникальных `(v,s,L)` в псевдослучайном порядке, seed фиксирован перед запуском; алгоритм тасования фиксируется вместе с версией генератора. Контрасты J-PT/J-VT на I/O формируют *сопоставимые по времени блоки*, для анализа используются **парные/блочные** повторения, а не независимые HTTP-запросы. В согласованной по охвату дополнительной серии J-PT/io и J-VT/io — 10 соответствующих блоков сетки ёмкости; результат одной ступени — отдельный новый запуск и один run_id. Порядок чередуется так, чтобы каждый SUT появлялся в начале и конце серий; все 4 SUT **никогда не работают одновременно**.

Независимый запуск = новый процесс/контейнер SUT после стандартизированного перезапуска, новые HTTP-запросы и отдельное окно; временная близость внутри блока сохраняет возможную корреляцию для парного анализа. Запись `seed`/`ordered_run_ids`, времени прогрева, окна, состояния CPU governor, температуры/частоты, фоновой нагрузки и хост-манифеста обязательна. Если частота/температура дрейфует, применяется заранее оговорённый *технический* критерий `invalid`/перепроверки, **не правило удаления неблагоприятных SUT-результатов**. Один и тот же прогон не используется дважды как статистически независимый.

## 7. Контроль стенда, A/A и техническая калибровка

| Испытание P0/P1 | Проверяемый сигнал | Условие допуска до M |
|---|---|---|
| Функциональная эквивалентность | `GET /io` → настоящий upstream и точный `{"scenario":"io","payload":"OK"}`; `GET /cpu` → канонический digest одного N; отказ эмулятора не даёт ложный 200 | **0 функциональных расхождений** в contract check, независимое повторение и негативный тест |
| Фактическая модель | `Thread.isVirtual()` для J-VT; платформа для J-PT; suspend/WebClient для Kotlin без `.block()` в I/O; goroutines и однотипный путь Go | Подтверждение диагностикой **вне M**, одинаковая сборка Java J-PT/J-VT |
| Калибровка CPU | Проверить 32 нулевых байта и независимый SHA; один N на заранее выбранном контрольном варианте для ~50–100 мс вычисления на малой нагрузке | Зафиксированный `N` и digest одинаковы у четырёх SUT; не делать индивидуальный подбор |
| k6 отдельно от SUT | На контролируемом быстром endpoint убедиться в подаче > проектного `λ_max`, CPU/RAM VU с запасом, нулевые drops в нормальном режиме | Инструмент не является лимитом до предполагаемой границы SUT |
| Эмулятор и сеть | `GET /delay` около 100 мс в низком режиме; пробная пиковая параллельность на уровне суммарных upstream-вызовов, p95/ошибки/CPU/RSS | Запас пропускной способности и стабильной задержки; конкретный допуск из P1/P2 |
| **A/A** | Два скрыто обозначенных набора **одной и той же J-PT конфигурации** на фиксированной нагрузке около границы; 10 новых независимых пар по блокам (кандидат) для p95/RPS/ресурсов. Если оценивается также шум **ёмкости C**, потребуется повторить A/A на отдельной сетке из нескольких ступеней, не делать вывод о разбросе C по одной λ | Интервалы эффекта A/A и заданная **заранее** граница практической эквивалентности; *отсутствие значимости НЕ доказывает эквивалентность*. При неприемлемом разбросе — улучшить изоляцию и/или увеличить повторы |
| Нагрузка мониторингом | Тот же J-PT режим с лёгкими метриками и с временно отключённым сбором для диагностического сравнения | Разница измерена и признана малой по границе P2, в M мониторинг одинаков |
| Границы окна | Совпадение UTC и monotonic, отправленных запросов и итогов, drain/timeouts, экспорт Prometheus | Ни потерянных и неучтённых запросов, ни разрыва обязательных временных рядов |

**Ожидаемая статистическая чувствительность:** до M на независимых A/A оценить разброс ёмкости/латентности и проверить моделированием/перестановками, хватает ли `10` блоков и шага сетки ≤5% для вывода при эффекте масштаба 15%. Для оценивания мощности следует рассматривать сценарии, **реально отличающиеся от границы H₀**, например `ρ = 1.30` как *иллюстративную* альтернативу; мощность обнаружить ровно `ρ=1.15` при тесте с нулевой границей `1.15` высокой быть не может. Проектный ориентир — мощность ≥80% при α=0.05 в таком сценарии, а не обещание её достижения. Если точности недостаточно, предложить изменение числа блоков, длительности или сетки **до M и отдельно согласовать**. A/A-данные никогда не дают научного ответа на J-VT против J-PT.

## 8. Статистическая обработка: точная единица анализа и интерпретация

### 8.1. Таблицы по каждой нагрузочной точке

Для каждого `(v,s,λ)` среди технически валидных прогонов: `n`, число `quality_pass`, медиана/среднее/SD/IQR `successful_rps`, `p50/p95/p99_success`, `errors_pct`, CPU core equivalents и RSS MiB; показать распределения точками и 95% интервалы для **прогонных** агрегатов (не делать 10 тысяч запросов = 10 тысяч независимых выборок). Сообщить, где ошибки/тайм-ауты, где насыщен SUT, где техническая браковка. Для основного сравнения на *одинаковом λ* p95/CPU/RAM исследуются как вторичные, без выдачи их за доказательство H₁ по `C`.

### 8.2. Оценка C и односторонний интервал для ρ (предложенная статистическая процедура)

1. После фиксации сетки P2 рассчитать `quality_pass` каждого прогона, по правилу ≥9/10 выбрать `λ*` и `λ_fail` из §3.2; отдельно сохранить статусы, величину достигнутого успешного RPS и ширину интервала. При отсутствии обеих границ → `not_testable` для первичного сравнения.
2. Для статистической неопределённости ресэмплировать **полные независимые блоки** `B1..B10` с возвращением (один и тот же индекс блока одновременно для J-PT и J-VT); внутри ресэмплированной таблицы пересчитывать прохождение ступеней, `C` и `ρ`. Проектно **10 000 bootstrap-повторов** с фиксированным seed; неверно ресэмплировать отдельные HTTP-запросы. Если ёмкость не определима в части реплик — это признак недостаточной информации, не основание тихо выбросить их; долю таких реплик опубликовать и при необходимости объявить результат неопределённым.
3. Проектный односторонний уровень `α = 0.05`. Нижнюю 95%-ю границу `ρ` оценить **блочным bootstrap** и дополнительно проверить *консервативную границу дискретности* из `last_pass_successful_rps` и `first_failed_target_rps` (при предварительно оправданной монотонности). Bootstrap не учитывает неиспытанный интервал сам по себе; если возможная ошибка сетки перекрывает 1.15, **не** подтверждать H₁. Рекомендуется имитационная проверка покрытия доверительного интервала на P1; при неудовлетворительном покрытии смена метода/числа повторов согласуется до M.
4. `supported`, только если: (a) обе границы ёмкости установлены без технической цензуры; (b) bootstrap/консервативная нижняя граница отношения убедительно **строго выше 1.15**; (c) при расчёте не было скрытого изменения критериев/сетки. Иначе `not_supported` (адекватно измерили, но доказательств недостаточно) или `undetermined/not_testable` (не установили `C`, сильное нарушение качества измерений или неоценимая неопределённость). **Ни один из этих исходов не доказывает H₀.**
5. В отчёте указать `C_PT`, `C_VT`, `ρ`, границы пройденной/непройденной λ, ширину сетки, полученную нижнюю CI, число валидных блоков и число bootstrap-реплик с неопределённой границей. Указать эффект в **% и запросах/с**, а не только `p-value`.

**Примечание о строгом смысле «максимума»:** полученная `C` — *максимальный подтверждённый устойчивый успешный RPS в пределах заранее испытанной сетки и данного стенда*, **не физическая универсальная ёмкость сервиса во всех условиях**. Утверждение о «точном максимуме» или перенос результатов на другое оборудование без опыта недопустимы. Ширина дискретного интервала — часть неопределённости.

### 8.3. Вторичные сравнения

Для K-CO и G-GO и **любых CPU-условий**: графики по одинаковым `L1–L3`, относительные эффекты на p95, успешном RPS, ошибках, CPU-секундах/успешный запрос и peak RSS с 95% интервалами на уровне блоков. **Дополнительной сетки и оценки `C` для этих условий нет.** Не называть наибольший из трёх успешно выдержанных уровней «максимальным устойчивым RPS». Межплатформенное смешение факторов Go/JVM сохраняется. Формальные вторичные проверки при необходимости использовать **Holm** для заранее перечисленного семейства попарных сравнений при α=0.05, а не неограниченный набор p-value. При отсутствии мощности — преимущественно описательная статистика без заявлений о «доказанной эквивалентности». Для CPU рост потоков не должен автоматически трактоваться как ускорение SHA-256.

**Механизм анализа:** исходные `k6.json`, `k6-summary.json`, `prometheus.json`, `sut.log`, манифесты SHA → `validate_runs.py` → `runs.csv` (включая valid/invalid), `capacity_estimates.csv` **(ровно два основных оцениваемых сочетания J-PT/io и J-VT/io; для остальных `not_estimated_by_design`)**, `comparisons.csv` → фигуры и отчёт. Все решения должны быть воспроизведены командой `make reproduce` из замороженного релиза; пилот запускается отдельной командой/профилем и не меняет `experiment.yaml` во время R.
